# Пороги по здоровому прогону

[← Оглавление](README.md) · [README](../../README.ru.md) · [English](../calibrate.md) · **Русский**

Абсолютные пороги хрупки. 16 мс на флагмане и на бюджетном телефоне — разные
вещи, и такой конфиг не переносится между устройствами. Более того, он не
переносится и между сценариями: для запуска за 772 мс и для минуты геймплея
понятие «долго» означает совершенно разное.

```bash
echolot calibrate run1.perfetto-trace run2.perfetto-trace -c echolot.yml
```

Детекторы запускаются с **открытыми** порогами, по каждому трейсу снимается
статистика столбца отчёта, медиана по трейсам представляет всю серию, и затем
применяется коэффициент запаса. Вывод представляет собой готовый раздел
`detectors:` с пояснением в каждой строке:

```yaml
detectors:
  frame_jank: false
  main_thread_block:
    min_slice_ms: 26.6    # top10(self_ms)=17.7 × 1.5, median of 5 run(s), sample 175 per run
  runnable_starvation:
    min_runnable_ms: 27.2    # top10(total_ms)=18.1 × 1.5, median of 5 run(s), sample 46–50 per run
    skip_glob: "*Binder*"    # from the config
```

Этот блок может полностью заменить соответствующий раздел конфига. Детектор,
выключенный в конфиге, возвращается как `false` и не измеряется; некалибруемые
параметры (маска, доля, детектор без `@calibrate`) переносятся без изменений;
а порог, который не удалось откалибровать, сохраняет значение из конфига как
настройку или встроенное значение по умолчанию в виде комментария.

Команда намеренно **не редактирует сам конфиг**. Пороги определяют, что
считать нормой, и такое решение нельзя отдавать скрипту: он печатает
предложение, человек смотрит на цифры и принимает решение.

## Как детектор объявляет калибровку

Рядом с порогом, в шапке SQL-файла:

```sql
-- @param: min_slice_ms = 16
-- @calibrate: min_slice_ms = top10(self_ms) * 1.5
```

Измерительный проход обнуляет калибруемые пороги, чтобы `HAVING` пропускал всё,
и убирает завершающий `LIMIT` — статистика по усечённому топ-20 была бы
статистикой только по верхушке хвоста.

Калибруются только те пороги, которые обнуление **открывает**. Относительный
параметр вроде `max_covered_pct` не калибруется: 50% остаются 50% на любом
устройстве, а обнуление полностью закрыло бы фильтр.

## Почему ранг лучше перцентиля

Поддерживаются обе формы:

```sql
-- @calibrate: min_slice_ms = top10(self_ms) * 1.5
-- @calibrate: min_slice_ms = p95(self_ms) * 1.5
```

По умолчанию используется `topN` — «N-е по величине значение». Это читается
как *на здоровом прогоне этот детектор должен выдавать не более N строк*, что
напрямую задаёт размер отчёта. Именно поэтому статистика берётся по каждому
прогону отдельно: `analyze` сворачивает повторы в одну строку на сущность, так
что размер отчёта соответствует одному прогону. Если объединить строки пяти
трейсов в один пул, каждое значение попадёт туда пять раз, `top10` окажется
около второго по величине значения одного прогона, и порог начнёт расти с
числом повторов — на холодных стартах демо-приложения это дало 4.7 по одному
трейсу и 170.3 по пяти.

Перцентиль на живых трейсах ведёт себя хуже, потому что зависит от размера
выборки — а он сильно скачет:

| сценарий | уникальных имён срезов | `p95` | `top10` |
|---|---|---|---|
| холодный старт | 175 | 26.9 ms | 26.6 ms |
| минута геймплея | 4729 | **0.8 ms** | 300.8 ms |

При 4729 группах выше p95 всё ещё остаётся больше двухсот строк — порог
перестаёт быть порогом. Ранг от размера популяции не зависит.

## Когда порог не выводится

Два случая, и оба честнее случайного числа.

**Выборка меньше `--min-sample`** (по умолчанию 10) в каждом прогоне.
Статистика по горстке значений — случайное число, притворяющееся обоснованным.
Размер выборки считается отдельно в каждом прогоне; прогон, где он меньше
минимума, исключается из медианы.

**Вырожденный хвост.** Выборка достаточна, но N-е значение уже близко к нулю.
Нулевой порог означает «сообщать обо всём», что не является порогом — на
здоровом прогоне этому детектору просто неоткуда взять число.

В обоих случаях в выводе сохраняется комментарий со значением по умолчанию и
причиной, а в конце добавляется итоговая строка.

Детектор, чей запрос **упал с ошибкой**, не относится ни к одному из этих
случаев: его ошибка печатается в stderr, в строке говорится, на скольких
трейсах он упал, и итог упоминает его. Если запрос упал на всех трейсах,
`calibrate` завершается с кодом 1.

## Калибруйте на повторах одного сценария

Смешивание холодного старта с минутой прокрутки даёт бессмысленные пороги.
Команда предупреждает, если окна расходятся более чем вдвое, но сбор
сопоставимых прогонов — задача `collect`.

Вот как это выглядит на практике для одного приложения на двух устройствах:

```
                       эмулятор   Galaxy A51
runnable_starvation        27.2          7.9
main_thread_block          26.6         36.5
binder_txn total           84.3         30.5
```

Два порога упали примерно втрое, а один вырос примерно на треть. Один конфиг с
абсолютными числами означал бы на этих двух машинах совершенно разное — в этом
и состоит главный довод в пользу этой команды.

## Несколько сценариев

Пороги не переносятся и между разными пользовательскими путями одного
приложения. Два сценария на одном Galaxy A51 и одной версии кода — холодный
старт и первый запуск после `pm clear` — откалибровались так:

```
                       холодный старт   первый запуск
runnable_starvation               3.6             9.8
uninstrumented_cpu               10.4            27.3
binder_txn total                  1.1             2.5
main_thread_block                17.8            21.5
```

При анализе с числами первого запуска холодный старт потерял 9 из 12 строк
`runnable_starvation` и 6 из 8 строк `uninstrumented_cpu`. А первый запуск с
порогами холодного старта выдал 30 и 20 строк вместо 13 и 7 — причём все они
были его обычной работой.

Поэтому в конфиге с `scenarios:` у каждого сценария может быть свой раздел
`detectors:`, накладываемый поверх верхнеуровневого только для этого сценария,
порог за порогом. Значение в сценарии побеждает, пропущенное берётся сверху,
`false` отключает детектор для этого сценария, а указание порогов включает
детектор, выключенный на верхнем уровне. Верхний раздел удобен для общих
настроек всех сценариев: масок и переключателей.

При использовании `scenarios:` `calibrate` выводит секцию измеренного сценария,
чтобы вставить её под этим сценарием рядом с `start` и `end`:

```yaml
scenarios:
  cold_start:
    detectors:
      main_thread_block:
        min_slice_ms: 17.8    # top10(self_ms)=11.9 × 1.5, median of 5 run(s), sample 246–254 per run
      main_thread_outlier:
        min_abs_ms: 40    # kept the default over the 2.8 in detectors: — top10(max_ms)=0.15, the tail of the distribution is degenerate
```

Переносится то, что уже было в секции сценария, а верхний уровень остаётся на
месте. Стоит пояснить одну строку: порог, для которого прогоны сценария не
дали числа, но который задан на верхнем уровне, возвращается со значением по
умолчанию как явная настройка. Без неё число с верхнего уровня просочилось бы в
сценарий через наложение: в примере выше холодный старт работал бы с порогом
2.8 мс от первого запуска там, где его собственные прогоны допускают только 40
по умолчанию. Удалите эту строку, если верхнее число задано вами намеренно для
всех сценариев.

В отчёте фиксируется, чьи пороги использовались: `params_source` принимает
значение `scenario` для детекторов с собственными порогами сценария, а строка
`Config:` в `report.md` пишет ``thresholds: scenario `cold_start`'s own for 5
of 14 detectors``. `echolot status` отмечает сценарии, у которых есть
собственные пороги. Конфиг с одним `scenario:` хранит пороги в верхнем
`detectors:`.

## Калибруйте на здоровых прогонах, а не на проблемных

Слово «здоровый» — суть всего метода. Пороги, выведенные из десяти трейсов с
регрессией, лягут *выше* регрессии, и `analyze` на них покажет чистый прогон —
планка окажется выставленной по самой проблеме. Калибруйте на заведомо
хорошей сборке; если её нет, оставьте значения по умолчанию и ищите проблему с
ними.

Чтобы проверить, что покажут встроенные пороги без изменения конфига,
запустите `analyze --defaults`; чтобы временно сдвинуть один порог на один
прогон — `analyze --set main_thread_block.min_slice_ms=16`. Оба режима
записываются в отчёт (`config.defaults`, `config.set`,
`detectors[].params_source`), чтобы такой отчёт нельзя было спутать со
штатным прогоном проекта.
