# Сравнение двух отчётов

[← Оглавление](README.md) · [README](../../README.ru.md) · [English](../compare.md) · **Русский**

`echolot analyze` отвечает, куда ушло время в одной серии трейсов. Но обычно
люди приходят с двумя половинами вопроса — *было 3 с, стало 7 с, куда ушли
эти 4 секунды* — и для второй половины нужны две серии.

`echolot compare` принимает два Marker Report и выдаёт одну таблицу,
отсортированную по величине сдвига каждой строки: сдвиги времени главного
потока, которые держатся, идут первыми, а сдвиги, которых прогоны не
подтверждают, — последними. Верхняя строка обычно и есть ответ.

```bash
echolot compare                       # открытое расследование: предыдущий раунд против последнего
echolot compare --hunt 3              # расследование 3: первый отчёт против последнего
echolot compare old.json              # этот отчёт против последнего отчёта его сценария
echolot compare old.json new.json     # ровно эти два отчёта
```

Без аргументов, при открытом расследовании, сравниваются два его последних
раунда среди отчётов, которые туда кладёт каждый `analyze --hunt <n>`.
`analyze` без этого флага работает вне расследования и ничего туда не кладёт.
Раунд — это записи, которые расследование читает впервые, с порогами из
конфига. Всё остальное — взгляд, и он пропускается: те же записи ещё раз, их
часть, часть их вперемешку с новыми или любой `analyze` с `--set` или
`--defaults`. Иначе взгляд на один трейс раунда 2 стал бы стороной «после», без
разброса, по которому судят о сдвиге.

Раунд это или взгляд, решает `analyze`, когда кладёт отчёт: по содержимому
записей, а не по путям — `collect --hunt` пишет каждый раунд под теми же
именами `<scenario>_iter000…`. Он говорит об этом в stderr, `[i] filed as round
3: …` или `[i] filed as a look, not a round: …`, и запись расследования это
хранит. Строка `compare` называет оба взятых отчёта и их раунды, а каждый
взгляд после старшего — с причиной. Если раундов меньше двух, берутся два
последних отчёта, и строка говорит, что есть что. Отчёт, положенный до того,
как `analyze` стал ставить эту пометку, различается по самому отчёту: взгляд,
если он сделан с `--set` или `--defaults` или если окно его первой записи
открылось в тот же момент того же процесса, что у раунда раньше. Тогда строка
говорит об этом: взгляд на часть раунда без его первой записи так сойдёт за
раунд. Для любой другой пары укажите два пути.

Команда пишет `comparison.md` и `comparison.json` рядом с отчётом (относительный
`-o` считается от каталога конфига). С двумя названными отчётами и без `-o` она
только печатает сравнение и ничего не пишет: эти два отчёта не последние для
сценария, а `comparison.*` рядом с отчётом стартовая страница показывает как
«After the fix». Для конфига с несколькими сценариями
сравнение идёт с последним отчётом того же сценария. Отчёты разных сценариев
или разных определений окна (см. [Два окна](#два-окна)) сравнивать запрещено.

## Что показывает таблица

| Where | Evidence | Detector | Before | After | Δ | N | Holds |
|---|---|---|---|---|---|---|---|
| SyncAdapterThre | — | uninstrumented_cpu | — | 1402.0 ±61 | **new** | — → 0 | — |
| TeamRepository.loadAll | com.example.app | main_thread_block | 12.1 ±2 | 883.4 ±40 | **+871.3 ×73.01** | 1 → 1 | yes, +831.3 … +911.3 |
| inflate | com.example.app | main_thread_block | 47.3 ±31 | 121.9 ±88 | +74.6 ×2.58 | 12 → 31 | no, -13.4 … +162.6 · ~8 runs a side |

**Одна таблица вместо секций по детекторам.** В сравнении вопрос один,
поэтому детектор переносится в отдельный столбец, а строки сортируются сквозным
образом.

**Метрика своя для каждого детектора.** Self time там, где детектор его
считает, иначе total time — так же, как сортируется сам отчёт.

**`N` — не украшение.** Удвоение `inflate` (`12 → 31`) означает, что метод
стал вызываться чаще. Рост `TeamRepository.loadAll` в 73 раза при `1 → 1`
означает, что замедлилась сама операция. Это разные баги в разных местах.

**`±` — максимальное отклонение повтора от медианы**, а не стандартное
отклонение. Точные значения по прогонам лежат в `comparison.json`.

**`Evidence`** заполняется только у детекторов, где `detail` входит в
идентичность строки (`main_thread_block` группирует по потокам).

Строка главного потока у `uninstrumented_cpu`, `runnable_starvation` и
`monitor_contention` называется `main`. В отчёте, записанном раньше, там стоит
имя потока по ядру; такая строка читается как `main` и сопоставляется, а не
пропадает с одной стороны и появляется с другой.

**Порядок.** Строки идут по величине сдвига в три части: сначала сдвиги
времени главного потока или кадров, которые держатся и составляют не меньше
двадцатой доли окна, — время, которое потратил сам сценарий; потом все
остальные; последними — сдвиги, которых прогоны не подтверждают (Holds — no).
По одной величине сумма по пулу потоков стояла выше причины, следствием
которой была: 400 мс сна на главном потоке в инициализаторе (+419 мс в
`main_thread_block`) оказывались девятыми, под `monitor_contention` по пулу
корутин (−4,0 с, держится: пока главный поток стоял, воркеры меньше спорили
за монитор). Теперь причина первая. Маленькие сдвиги на главном потоке
(меньше двадцатой доли окна) остаются на своём месте, чтобы причина вне
главного потока — потоки, которые жгут CPU, — не ушла ниже. При слишком
малом числе прогонов для Holds ничего не держится, и порядок — по величине.
Чьё это время, говорит поле `on_main` в `comparison.json`.

**Маркеры.** Таблица маркеров из отчёта (домены из конфига и временные
маркеры) сравнивается отдельной секцией «Markers» под основной таблицей:
строки сопоставляются по имени и оцениваются по self time, как строки
детектора, а столбец Calls отдельно оценивает число вызовов за прогон
(«загрузка шла дважды вместо одного раза»). Для асинхронных секций
(`Trace.beginAsyncSection`) это единственное место, где они вообще
измеряются: детекторы их не читают.

**Имена только с одной стороны.** Срез, который не читает ни один детектор,
в таблицу не попадает, как бы ясно он ни отличал две сборки. Цикл на 200 мс,
вставленный в главный поток без своей секции, удлинил окно на 277 мс и не дал
строки ни с одной стороны; единственным именем, которое было во всех десяти
трейсах «после» и ни в одном из десяти «до», оказалась JIT-компиляция метода с
этим циклом — то есть место в коде. Поэтому `analyze` хранит имена срезов окна
(потоковых и асинхронных), а `compare` отдельной секцией «Names on one side
only» перечисляет имена, которые есть в каждом прогоне одной стороны и ни в
одном прогоне другой, — с числом прогонов (`3/3 against 0/3`), медианой за
прогон, самым длинным вхождением и потоком. Все числа в имени сворачиваются, и
каталог, куда Android ставит APK (он новый при каждой установке), тоже; свои
маркеры проекта остаются как есть. Имя попадает в список, если занимает от
1 мс за прогон, а другая сторона не держит его ни в одном прогоне вообще;
имя, которое у другой стороны было короче миллисекунды, выросло, а не
появилось. Имена, которые таблицы выше уже показывают как новые или ушедшие,
не повторяются. Нужно не меньше трёх прогонов с каждой стороны (две половины
десяти холодных стартов одной сборки дали около ста таких имён при одном
прогоне на сторону, 5–17 при двух, 3–4 при трёх и не больше одного начиная с
четырёх), иначе секция говорит, что не искала; с пяти прогонов имени
разрешено не быть в одном из них. В сравнении — до десяти имён на сторону,
`echolot compare … --names` печатает все вместо сравнения, а в
`comparison.json` они под ключом `names`. Отчёт, записанный до того, как имена
стали храниться, сравнивается без секции.

В `report.json` имена лежат в `slice_names`: `rows_gz` — имена из всех
прогонов, кроме, может быть, одного, от `floor_ms` за прогон, с их числами
(gzip-JSON в base64), и `seen` — все имена любого прогона, как первые четыре
байта SHA-1 (base64). Имени другой стороны, которого нет в `seen`, не было ни
в одном прогоне; совпадение четырёх байт случается примерно раз на четыре
миллиарда, и тогда имя пропускается, а не выдумывается. Упаковано потому, что
отчёт должен оставаться маленьким: десять холодных стартов загруженного
приложения дали 17 753 имени, и 946 строк в виде JSON заняли бы 228 КБ рядом с
285 КБ остального отчёта; упакованные `rows_gz` и `seen` — 133 КБ.

## Столбец Holds

Решает, можно ли доверять сдвигу. Показывает 95%-й доверительный интервал
(оценка Ходжеса–Лемана и интервал Мозеса без предположений о нормальности
распределения):

`yes` — весь интервал дальше порога, по которому строка попала в таблицу
(5 мс или 10%, большее), а не просто по одну сторону от нуля:

| значение | смысл |
|---|---|
| `yes, +831.3 … +911.3` | весь интервал за порогом: сдвиг воспроизводится при перезаписи |
| `no, +6.0 … +27.0 · floor 10.0 · ~13 runs a side` | интервал не пересекает ноль, но не выходит за порог. В сборке, сравнённой сама с собой, таких строк большинство среди не пересекающих ноль |
| `no, -13.4 … +162.6 · ~8 runs a side` | интервал пересекает ноль: разброс между прогонами больше самого сдвига, нужно ~8 прогонов с каждой стороны |
| `no, … · ~1 more after` | то же при 15 прогонах до и 4 после: хватит одного прогона после |
| `no, … · more runs will not settle it` | понадобилось бы больше сотни прогонов с каждой стороны |
| `—` | нечего проверять: строка есть только на одной стороне, либо прогонов слишком мало |

Строка под заголовком говорит, что спрашивал столбец и что осталось за
бортом: `Holds asks each range to clear the floor, not zero: 3 of 61 row(s)
with a verdict do, and 5 more that clear zero alone read no.`

Почему порог, а не ноль. При 95% до одной строки из двадцати, которая не
сдвигалась, ложится по одну сторону от нуля случайно, а сравнение судит все
строки обеих сторон — около двухсот на холодном старте большого приложения.
Три набора по 15 холодных стартов одной сборки, каждый разбитый случайно 7
против 8 сто раз, давали против нуля 4,0 таких строки на разбиение (3,0 из них
выше порога), против порога — 0,5; 5 против 5 — 1,3 вместо 5,8; 4 против 4 —
1,3 вместо 4,9. Строка, замедленная вдвое на стороне «после», держалась в 88
разбиениях из ста против 91 раньше. Поправка Бенджамини–Хохберга на 5% по
строкам выше порога оставляла 0,1 ложной строки, но вдвое замедленная
держалась лишь в 59, а при 5 против 5 — ни в одном: самая малая вероятность,
доступная строке, 0,008, больше того, что требуют шестьдесят строк сразу.

Эти числа — одного приложения на одном телефоне. Сколько строк держится без
всяких изменений в вашем сценарии и какой порог их гасит, измеряет
`analyze --noise` на уже записанном наборе: см.
[Собственный шум сценария](#собственный-шум-сценария).

Для 95%-й уверенности достаточно 4 прогонов с каждой стороны (или `3` против
`5`, `2` против `8`, `1` против `39`). Число прогонов в ячейке — порядок
величины, а не обещание: от 4–5 прогонов интервал движется целыми шагами.
При неравных сторонах оно идёт туда, где дешевле: 15 до и 4 после
разбрасываются как 6⅓ с каждой стороны, и сдвигу, которому нужно 7 с каждой,
хватит одного прогона после (`~1 more after`).

## Окно и старт

Две строки над таблицей проверяются так же, как строка: тот же `change`
против того же порога, тот же интервал и тот же вердикт Holds — по окну (и
старту) каждого прогона, которые `analyze` теперь хранит в `report.json`:
`window.values` — окно каждого прогона в порядке `traces`,
`window.startup.values` — старт каждого прогона, `reason_values` — каждая
причина старта по прогонам (прогон без причины — 0, как её считает медиана).

```
Scenario window: **1012.0 → 1313.5 ms**  (+301.5, ×1.3) · holds: yes, +225.0 … +374.0
Startup (platform): **1072.0 → 1373.5 ms**  (+301.5, ×1.28) · holds: yes, +225.0 … +374.0
```

Это прогоны фикстуры, по четыре на сторону, сторона «после» медленнее на
300 мс; `doctor` это проверяет. Те же восемь прогонов, разбитые четыре на
четыре без изменений, расходятся на 1,5 мс, и их интервал `-75.0 … +74.0`
пересекает ноль: `holds: no`. Заложенная в демо блокировка удлиняет запуск
на 24 мс, и окно читается `holds: no, -54.0 … +105.7`, хотя две строки
самой блокировки держатся: изменение настоящее и меньше того, что пять
запусков видят во всём окне.

Раньше окно было единственным числом, которое `compare` не проверял: 15
холодных стартов против 4 у следующей сборки давали
`5700.0 → 5310.0 ms (−390.0, ×0.93)` и больше ничего, а старт платформы, в
той паре изменившийся сильнее всего (на 35%), не сравнивался вовсе.

На настоящих прогонах: холодный старт одного приложения до первого
экрана, около 4,9 с, шесть контрольных наборов по десять запусков и четыре
набора со сном на главном потоке при старте, 50, 100, 200 и 400 мс.
Контроли друг против друга: окно держится в 1 паре из 15 и в 24 из 756
разбиений каждого контроля пять на пять (3,2%). Сон против каждого
контроля, по десять на сторону: 50 и 100 мс не держатся ни в одной паре,
200 мс — в 4 из 6, 400 мс — в 6 из 6; по пять на сторону 400 мс — в 2 из 6.
Старт (около 1,2 с, без меню после него) видит больше: от 100 мс — 6 из 6,
50 мс — 3; контроли держатся в 3 парах из 15 (сдвиги 27–41 мс между
наборами, записанными в разное время: настоящие, но не приложения).

Окно и старт держатся против нуля, а не против порога строки: это одно
число и одна проверка, а не одна из двухсот строк, проверяемых разом. Порог
в десятую часть окна 4,9 с — 490 мс, и против него сон в 400 мс не держался
бы ни в одной паре вместо всех шести. Причины старта — дюжина проверок
разом, и для них действует правило строк.

Строка `Startup (platform)` есть, когда старт есть у обеих сторон; разные
типы старта названы в ней, `(cold → warm)`. Причины старта
(`bind_application`, `io`, `binder`, время до запуска процесса и прочие
части разбивки Perfetto) судятся как строки, в отдельной таблице
«Startup by reason» под основной — те, что сдвинулись выше порога. В
таблицу детекторов они не входят: это то же время, что уже считают строки
детекторов (`io` — ожидания диска, `binder` — вызовы), и счётчики таблицы и
суммы простого чтения посчитали бы его дважды.

Отчёт без значений по прогонам (записанный до них) сравнивается как раньше —
две медианы и их разность, — а строка говорит, что сдвиг не проверен:
`· untested: the before report keeps no per-run values; ...`. Слишком мало
прогонов, два отчёта не об одном или сторона, не сказавшая, какой echolot её
написал, оставляют окно без вердикта, как и каждую строку.

## Что вообще считается сдвигом

Строка попадает в таблицу, если сдвинулась больше чем на **5 мс или 10%**
(берётся большее значение), что настраивается через `--floor-ms` и
`--floor-pct`. Всё ниже порога суммируется и приводится одной строкой под
**Steady**. Частота повторения (`1/5 → 5/5`) тоже учитывается: отсутствующие
повторы считаются за ноль, поэтому строка, появившаяся во всех 5 прогонах
вместо 1 из 5, попадёт в выросшие. Относительный порог — десятая часть
значения **до**, поэтому те же два отчёта, сравнённые в обратном порядке,
дают немного другие пороги, и несколько строк рядом с ними переходят через
них (93 сдвинувшиеся строки в одну сторону, 91 в другую). Это ожидаемо.

## Та же работа под новым именем

Воркеры пула меняют номера (`arch_disk_io_0` и `arch_disk_io_3`). Поэтому
строки сопоставляются в два прохода: сначала по точному имени, затем по
семейству (сворачивая цифры, кроме маркеров с префиксом `AGENTTMP_`), если
пара однозначна — такие строки помечаются `*(family)*`.

## Когда два отчёта нельзя сравнивать

Даже если сравнение возможно численно, наверху перечисляются все
предупреждения:

| предупреждение | почему это важно |
|---|---|
| `process` | два разных приложения (`comparable: false`, колонка Holds пуста) |
| `window` | окна определены по-разному (`comparable: false`, `echolot compare` отказывает сразу) |
| `thresholds` | отличаются параметры детекторов (`--defaults` выравнивает их) |
| `defaults` | одна сторона считалась с `--defaults`, другая без |
| `config` | изменился хэш конфига; что видно по самим отчётам (glob якоря, путь конфига), названо |
| `anchor-before` / `anchor-after` | якорь не нашёлся ни в одном повторе, окно уехало к краю трейса: `comparable: false`, колонка Holds пуста. Если в трейсах нет и запуска приложения, названа настройка раннера (`runner.reset_policy`), а не конфиг. Якорь, не найденный лишь в части повторов, называется так («not found in 1 of 15 after repeats»): пара остаётся сравнимой, а совет — убрать эти трейсы (тёплые, если в наборе смешаны холодные и тёплые запуски) |
| `runs` | разное число повторов |
| `single` | по одному трейсу на стороне (нет разброса, `Holds` пуст) |
| `few` | слишком мало повторов для 95%-й оценки |
| `detectors` | разный набор детекторов |
| `detector-failed` | детектор упал на одной из сторон (его строки исключены из таблицы) |
| `not-checked-before` / `not-checked-after` | детектор не мог проверять из-за отсутствия данных в трейсе (исключён с обеих сторон) |
| `frames` | одна сторона нарисовала в окне меньше кадров (на относительный порог и больше): работа «раз на кадр» уменьшилась только поэтому. Строки, чьё число повторов пошло вслед за кадрами, показаны со временем на одно повторение (`per_occurrence`) и без вердикта по сумме; первыми идут строки, сдвинувшиеся против кадров |
| `instrumentation` | появились временные маркеры `instrumentation.temp_prefix`; слайсы, в которых они лежат напрямую, тоже названы: их self time ушёл в маркеры, поэтому эти строки оцениваются по total (в таблице `*(by total)*`) |
| `instrumentation-removed` | временные маркеры убраны между раундами: это не ушедшая работа, а слайсы, где они лежали, оцениваются по total |
| `environment` | частота CPU изменилась на ≥10% (или не записана на одной из сторон) — замедление может быть из-за устройства, а не кода |
| `environment-thermal` | устройство троттлило в одной серии и не троттлило в другой (только когда обе стороны записали температуру) |
| `environment-thermal-one-side` | устройство троттлило в одной серии, а у другой нет записи температуры вовсе: сказано, в скольких повторах, и что на другой стороне троттлинг нельзя исключить — без утверждения, что там было прохладно |
| `environment-load` | другие процессы заняли 40% времени процессоров в окне одной из сторон или больше, на 15 пунктов больше, чем в другой: эта сторона записана на занятом устройстве. Процессы, которые рисуют приложение и пишут трейс, — SurfaceFlinger, HAL композитора, system_server, SystemUI, лаунчер — не считаются: запуск занимает их и на спокойном телефоне. Отчёт, где они ещё считались, с новым не сравнивается |
| `sampling` | сэмплинг стеков был включён только на одной стороне или с другой частотой |
| `compose_names` | в одной серии писались имена composable-функций, в другой нет |
| `compile` | разный уровень компиляции ART (`speed-profile`, `verify`, `run-from-apk`); если трейс начался при уже запущенном процессе и уровня не знает, сравнивается работа JIT в окне: в три раза больше методов и не меньше 50 разницы — предупреждение |
| `recording` | серии записаны по-разному: другой раннер или `reset_policy`; force-stop перед повтором застал приложение запущенным на одной стороне и уже остановленным на другой; телефон на зарядке на одной стороне и на батарее на другой или экономия заряда только на одной; другой конфиг трейса — источники данных, категории atrace, события ftrace, названные на той стороне, где они были; телефон настроен иначе — другие масштабы анимаций или «Не сохранять действия» только на одной стороне. Детекторы, которые читают то, что записала только одна сторона, названы |
| `recording-mixed` | повторы одной стороны записаны не одинаково (раннер, `reset_policy`, питание, экономия заряда, конфиг трейса или настройки телефона): её медианы смешивают два способа записи |
| `recording-unknown` | одна сторона не может сказать, как записана, а другая может: отчёт старше блока `recording`, трейсы записаны до того, как `collect` стал класть рядом свой файл, или не `collect`, или трейс без собственного конфига, или `collect` ещё не читал настройки телефона |
| `version` | отчёты написаны разными версиями echolot, или один не говорит какой. Если сторона не говорит, вердикта нет ни у одной строки: какие её детекторы читали трейс так же, неизвестно — проанализируйте её трейсы заново |
| `detector-changed` | детектор читал трейс разным кодом на двух сторонах (`sha` в отчёте): его строки остаются, вердикта у них нет |
| `same-traces` | обе стороны — одни и те же записи: те же имена трейсов, тот же pid и то же окно с точностью до сотой миллисекунды. Всё, что сдвинулось, — от инструмента или конфига, вердикта нет ни у одной строки |
| `drift` | повторы одной стороны или обеих дрейфуют от первого к последнему: строки, найденные в каждом повторе, следуют порядку повторов теснее, чем дал бы случай, поэтому медианы этой стороны не описывают одного состояния устройства, и строка, дрейфующая вместе с ней, может «держаться» без всяких изменений. Названы `p` каждой стороны и строки, ближе всего идущие за порядком; вердикты остаются — см. [Повторы, которые дрейфуют](#повторы-которые-дрейфуют) |

### Как записаны две стороны

В каждом отчёте есть блок `recording`. В нём то, что конфиг самого трейса
попросил у устройства: источники данных, категории atrace и события ftrace.
И то, что `collect` знал о каждом повторе. Это он кладёт рядом с трейсом в
`<трейс>.recording.json`: раннер, `reset_policy` и застал ли force-stop перед
повтором приложение запущенным.

Последнее появилось из-за пары, где больше ничего не различалось. Один и тот
же APK на SM-A515F записали в два дня с одним конфигом. Все старты холодные,
троттлинг одинаковый. В первый день — обычный `collect`: его force-stop в 14 из
15 повторов застал приложение запущенным с прошлого повтора, и каждый старт шёл
через полсекунды после kill. Во второй день скрипт сначала останавливал
приложение и пятнадцать раз запускал `collect -n 1`. Окно во второй день вышло
на 0.68 с короче, сравнение показало 60 строк с `holds: yes` и ни одного
предупреждения. Ожидания охлаждения между остановкой и стартом не было ни в
один из дней; повтор, который ждёт охлаждения, теперь начинается намного
позже остановки, потому что `collect` останавливает приложение до охлаждения.
Застала ли остановка приложение запущенным, теперь записано, и разница
названа. Сторона берётся по
большинству повторов: первый повтор любого `collect` застаёт приложение таким,
каким его оставили до запуска.

Настройки телефона там по той же причине: трейс не несёт ни одной.
`collect` раз за раунд читает масштабы анимаций из параметров разработчика и
«Не сохранять действия» (см. [Сбор трейсов](collecting.md)). Прокрутка списка
на SM-A515F со всеми тремя масштабами на 5 на одной стороне и на 1 на другой
дала от 5 до 17 строк с `holds: yes` — работа анимаций Compose, поток GPU, — и
ничто не говорило, что на одной стороне каждая анимация шла в пять раз
дольше. «Не сохранять действия» уничтожает активность, как только та уходит с
экрана, поэтому сценарий, который возвращается в приложение, мерит тёплый
старт там, где другая сторона мерила горячий. И то и другое названо со
значениями обеих сторон, а вердикты остаются, как при любом различии
`recording`.

Набор от `collect`, который уже клал справку, но ещё не читал настройки
телефона, говорит, как его записали, но не это, и получает свой
`recording-unknown`: настройки проверить нельзя, а это не то же самое, что
они совпали. Раунд макробенчмарка их не читает и неизвестным за это не
называется.

### Какой echolot написал каждый

Каждый отчёт говорит, какой echolot его написал (`toolchain.echolot`), а каждый
детектор — каким кодом читал трейс (`sha`: его запросы, `@identity` и модули
stdlib, без строк комментариев). Две версии, у которых отличается детектор,
читают один трейс по-разному: отчёты 0.7.0 и 0.17.0 по одним и тем же 15
трейсам дали 11 строк с `holds: yes`. У детектора с другим `sha` строки
остаются, вердикта нет. Отчёт, который не говорит, какой echolot его написал,
лишает вердикта все строки — проанализируйте его трейсы заново. Два отчёта,
оба старше этой отметки, сравниваются как раньше.

`same-traces` работает и на старых отчётах: те же имена трейсов, тот же pid
и то же окно (медиана, минимум и максимум) до сотой миллисекунды — это одни и
те же записи, прочитанные дважды.

### Повторы, которые дрейфуют

Колонка Holds считает повторы стороны одинаковыми: любой мог быть первым.
Сторона, записанная на устройстве, которое от первого повтора к последнему
прогревалось, нагревалось или успокаивалось, — это наклон, и половины одного
такого набора, сравнённые друг с другом, дали 12 и 7 строк выше порога, а
случайное разбиение тех же повторов — 3 и 1. До и после записываются одно за
другим, так что сравнение получает наклон целиком, сверх того, что устройство
делало между двумя сессиями.

Каждый отчёт говорит, дрейфуют ли его повторы (см.
[Повторы, которые дрейфуют](analysing.md#повторы-которые-дрейфуют-от-первого-к-последнему)),
а `drift` повторяет это здесь для любой стороны:

```text
> ⚠️ The runs before drift from the first to the last (before, p = 0.026 — closest: `io_wait` com.example.app · main 610.3 → 687.1 ms (ρ +0.74); …). A median over such runs is no one state of the device: rows that drift with them can read as moved, and hold, with nothing changed in the app. Before acting on a row that holds, record the two sides back to back and compare again.
```

Отчёт, написанный до этой проверки, читается на месте — по значениям повторов,
которые он уже хранит, так что и старая пара получает предупреждение.
Вердикты остаются, как и при всех условиях выше. Проверка видит наклон внутри
стороны, но не ступеньку между двумя сессиями, каждая из которых ровная сама
по себе: этого не покажет ни один отчёт одной стороны. Запись двух сторон
подряд это сужает: один APK против самого себя на раннере launch дал 3 строки
из 205 подряд и 31 из 203 через час.

### Собственный шум сценария

Сколько строк держится, когда ничего не менялось, выше измерено на одном
приложении и одном телефоне. В другом сценарии это другое число: оно зависит
от разброса повторов, числа строк и устройства. Читателю `holds: yes` в своём
сравнении нужно своё, и `analyze --noise` меряет его на уже записанном наборе:

```bash
echolot analyze .echolot/traces/cold_start-20261120-101245 --noise
```

После отчёта он много раз делит повторы набора на две половины, сливает каждую
так, как `analyze` сливает набор, и сравнивает их так, как `compare`, с тем же
порогом. Между половинами ничего не менялось, поэтому каждая строка, которая
держится, — шум. Вывод — таблица на английском, как у остальных команд:
медиана и 95-й перцентиль по случайным разбиениям (сколько строк с вердиктом,
сколько держится и какая это доля), в скольких разбиениях держалась хоть одна
строка, сколько раз держалось окно, и то же для разбиения по порядку.

**Случайно.** Двести разбиений из фиксированного seed, без повторов; «до» —
половина, где повторов меньше. Если разбиений не больше двухсот, берутся все
(восемь повторов делятся 35 способами, пятнадцать — 6435). Главное число —
в скольких разбиениях держалась хоть одна строка: на реальных наборах
большинство разбиений держит несколько строк, и одинокий `yes` в сравнении
своего сценария нужно читать с этим в виду. Окно, как и в `compare`,
проверяется против нуля, поэтому примерно одно разбиение из двадцати держит
его случайно.

**Первые против последних.** Набор из одной папки режется посередине — это
[дрейф](#повторы-которые-дрейфуют) отчёта в единицах сравнения. Набор из
нескольких папок, как `collect` откладывает каждый раунд, режется там, где
кончается папка, ближайшая к середине:

```bash
echolot analyze .echolot/traces/cold_start-20261120-101245 .echolot/traces/cold_start-20261120-114012 --noise
```

Это две сессии одной сборки друг против друга — ровно то, что получат «до» и
«после», записанные порознь, когда ничего не менялось; случайные половины
смешивают сессии и этого не покажут. Рядом — сколько случайных разбиений
держали столько же строк или больше: если одно из двадцати или меньше,
разрез по порядку не случаен, и строка вывода говорит, что делать: смотреть
дрейф или записывать стороны подряд.

**Порог.** Наименьший `--floor-ms`, при котором медианное случайное
разбиение не держит ни одной строки. Для каждой удержавшейся строки
`noise.json` хранит, насколько её интервал ушёл от нуля (`clears_ms`): такой
абсолютный порог ей нужен, чтобы перестать держаться. Поэтому один прогон
отвечает за любой порог выше того, с которым он сделан. Только абсолютная
часть: `--floor-pct` остаётся как есть.

**На каких размерах.** Половины: семь против восьми для набора из пятнадцати.
Сравнение пятнадцати с пятнадцатью различает сдвиги меньше и случайно
держит чуть меньше, так что половины для него читают чуть с запасом; размеры
названы в таблице. Нужно восемь повторов или больше — четыре с каждой
стороны; с меньшим числом трейсов `analyze` отказывает до чтения.

**Сколько стоит.** Ни один трейс не читается повторно: разбиение — два
слияния и одно сравнение отчётов повторов, которые `analyze` уже держит.
Около шестой доли секунды на набор из пятнадцати по триста строк, то есть
двести разбиений добавляют к разбору примерно полминуты. `--splits N` меняет
число разбиений, `--seed N` — выборку; тот же набор, число и seed дают те же
числа. Имена срезов только с одной стороны не считаются: это список рядом с
таблицей, у его строк нет вердикта.

**Почему `analyze`, а не `compare`.** Половину нужно слить из повторов.
Слитый отчёт хранит значения строки по повторам, но не номер повтора там, где
строку нашли не во всех, поэтому его не разрезать обратно на половины;
отчёты повторов `analyze` держит прямо перед слиянием.

Рядом с отчётом пишутся `noise.md` (то, что напечатано) и `noise.json`;
поля описаны в [английской версии](../compare.md#this-scenarios-own-noise).

### Два окна

При `scenario.window: launch` отчёт может закрыться по первому кадру
(`launch`), по `reportFullyDrawn()` (`launch+reportFullyDrawn`) или в конце
запуска, которому приложение само передало старт после первого кадра
(`launch+handover`, см.
[Старт, который приложение передаёт дальше](analysing.md#старт-который-приложение-передаёт-дальше)).
Они различаются по длине (на замерах разница медиан между первыми двумя
составляла ~56 мс), поэтому `echolot compare` отказывает в сравнении отчётов
с разными `defined_by` с кодом 2. Чтобы сравнить изменение, добавляющее или
убирающее `reportFullyDrawn()` или заставку, которая передаёт старт, задайте
явные `start` и `end` в сценарии. Отчёт, написанный до того, как echolot
стал идти за передачей старта, называет `launch` старт, закрытый на кадре
заставки: разберите его трейсы заново, прежде чем сравнивать с новым.

Отчёт по всему трейсу (`analyze --whole-trace` или `window: whole`,
`defined_by: "whole"`) не сравнивается с отчётом по любому другому окну: одна
сторона — о сценарии, другая — обо всём, что приложение делало, пока шла
запись. `compare` отказывает с кодом 2 и подсказывает разобрать обе стороны
одинаково: обе с `--whole-trace` или обе по окну сценария. Два отчёта по
всему трейсу сравниваются как обычно.

## Простое чтение

`echolot compare --plain` (или `--html`) переводит сравнение в понятный
человеку вердикт без участия LLM, сравнивая суммы строк по каждому детектору
(требуется минимум 3 запуска с каждой стороны, изменение ≥20%): `better`,
`worse`, `gone`, `new`, `no change`, `not compared`, `fine both times`,
`not checked`. `not compared` — проверка смотрела оба раза, но не одной меркой:
между сторонами поменялись её пороги, версия echolot, которая её читала, или
обе стороны — одни и те же записи. Что сдвинулось, сдвинул конфиг или
инструмент, поэтому ни лучше, ни хуже она не названа. Для одних и тех же
записей это говорит и вердикт наверху (#713).
Среди заметок под вердиктом — работа, которая есть только у одной стороны:
до трёх имён на сторону из секции «Names on one side only» (их не читает ни
одна проверка, поэтому ни одна из-за них не сдвигается). Заметка говорит, в
скольких прогонах своей стороны были имена, как столбец Runs таблицы: «In every
run after», «In 4 of 5 runs after», если каждое пропустило один прогон, и «In
every run after, or all but one», если такие смешаны, — тогда рядом с каждым
названным именем, пропустившим прогон, стоит `in 4 of 5`.

Детектор измеряет каждую строку, а пороги только отмечают, какие показать
(#832). Строка, которая есть только в одном отчёте, ищется в том, что другая
сторона намерила и не показала: `below` в `report.json`, все строки не меньше
`floor_ms`, 1 мс, которые не показал ни один повтор, без улик. Нашлась —
сравнивается с тем, что там намерено, и таблица помечает эту сторону
*(under the bar)*: 86 вызовов системы на 83 мс после исправления, каждый
короче порога 14,4 мс, — это строка, которая уменьшилась со 111 мс, а не
пропала со всеми 111 мс. Не нашлась — там она заняла меньше 1 мс. Строка,
которая есть только у одной стороны и сама не больше порога сдвига,
считается не сдвинувшейся: больше порога она сдвинуться не могла (#843). Отчёт echolot 0.18 и раньше хранит найденное под порогом только от
5 мс, не больше 200 строк, и читается как раньше.

Вердикт выносится по длине окна сценария. Окно без конечного якоря (или с
якорем, который не нашёлся) длится столько же, сколько запись, а
скриптованный скролл или драг пишется фиксированное время, поэтому такое
окно судится по доле кадров, которые приложение само сделало поздними
(`window.frames.late`: кадры, которые строки `frame_jank` помечают
`Self Jank`, по прогонам). Правило то же, что у окна: доли различаются на
пятую часть и больше, и не меньше чем на кадр из ста, а больше половины
прогонов лучшей стороны лучше лучшего прогона худшей. Пять пар наборов
одного драга (сборка с лишними рекомпозициями против сборки до неё и
исправления после) раньше все читались как «No clear change», окно
расходилось не больше чем на 8,6 мс, а доля поздних кадров шла 3% → 21% → 10%.
Доля стороны в предложении — медиана долей её прогонов, а числа рядом — того
прогона, который посередине по этой доле («21 of 650 frames in the middle
run»); при чётном числе прогонов — двух средних, и доля ровно между ними. Не
медиана поздних кадров на медиану нарисованных: это два других прогона, и
поздние 4, 3, 4, 3, 3 из 16, 15, 15, 16, 16 кадров читались как «20% … 3 of
16», а это 19%.

Если оба отчёта хранят окно каждого прогона, сдвиг окна ещё и должен
держаться ([окно и старт](#окно-и-старт)): сдвиг, чей интервал пересекает
ноль, — «No clear change», как бы далеко ни разошлись медианы, и
предложение называет интервал; так вердикт не утверждает того, что
отрицает Holds рядом с окном. При 4–6 запусках на сторону одного запуска,
медленного как у другой стороны, хватает, чтобы интервал пересёк ноль; с
семи — уже нет. Держащийся сдвиг сам по себе изменением не называется:
одна сборка в два дня расходилась до 18%, и каждый запуск одного дня был
медленнее каждого запуска другого — для этого и нужна пятая часть. Без
интервала (меньше четырёх запусков на сторону или старый отчёт) решают
прежние три условия.

Проверка со строками и на главном потоке, и на других (`monitor_contention`,
`runnable_starvation`, `uninstrumented_cpu` и другие, что называют поток)
судится по строкам главного потока, когда они сдвинулись, а сумма не пошла
туда же: ожидание главного потока на мониторе +300 мс при −4,3 с ожидания в
пуле корутин теперь читается как `worse`, и предложение называет обе части.

## Сравнение в виде страницы

```bash
echolot compare old.json new.json --html      # comparison.html рядом с comparison.json
```

Создаёт автономный HTML-файл `comparison.html` (тот же, что открывается во
вкладке **After the fix** в `echolot ui`): с графиком окна до/после,
фильтром по изменению, развёрнутой панелью графиков по каждому запуску и
вложенным `comparison.md`.

## JSON сравнения

`comparison.json` (схема 2) содержит `comparable`, `warnings`, `window`
(медианы, `delta_ms`, `ratio`, а ещё, как у строки, `change`, `shift` и
`holds`; `untested` — сторона, чей отчёт не хранит значений по прогонам),
`startup` (то же для старта платформы, `type` обеих сторон и `reasons` —
причины старта такими же строками; `null`, если старта нет хотя бы у одной
стороны), `summary` (включая `not_compared`, `state_changed`, `silent_both`,
`markers_moved`, `only_after`, `only_before`), `markers` (таблица маркеров по
обеим сторонам, с `calls`), `names` (имена только с одной стороны: `after` и
`before` со строками `name`, `runs`, `other`, `total_ms`, `max_ms`, `threads`;
`runs`, `floor_ms`, `least_runs` и `too_few`; `null`, если в одном из отчётов
имён нет) и `rows`
с полями `change` (`appeared`, `grew`, `shrank`, `vanished`, `steady`),
`shift` (`ms`, `low_ms`, `high_ms`, `floor_ms`, `resolves_ms`, `runs_needed`,
`more_runs`), `holds` и `on_main` (время главного потока или кадров).
`holds: true` — интервал за `shift.floor_ms` по одну сторону;
`holds_against: "floor"` наверху говорит, что файл записан так. В сравнении
без этого поля строки держались против нуля (`low_ms > 0 || high_ms < 0`).
`more_runs` — сколько ещё прогонов на каждую сторону (`{"before": 0,
"after": 1}`), `null` после сотни с каждой стороны. При `--plain`/`--html`
добавляется секция `plain`; у её заметки `unlike` есть `warnings` — id
предупреждений, которые она называет; у её `verdict` есть `by` (`window` или `frames`)
и, если окно идёт до конца записи, `frames` с поздними кадрами каждой
стороны (`late` и `count` — медианы, `share` с `low` и `high` по прогонам,
`runs` и `middle` — `late` и `count` прогона, чья это доля, или двух, между
которыми она ровно посередине), а у проверки, судимой по главному потоку, — `main`.

## Почему в CI намеренно нет gate

`analyze` и `compare` никогда не роняют сборку из-за медленного прогона.
На общих CI-раннерах пороги срабатывают на шум самой виртуальной машины;
кроме того, перцентили уже считает сам Macrobenchmark. Задача echolot в CI —
дать ответ *почему* замедлилось, а не стоять простым пороговым барьером.
Единственный gate в этом репозитории — порог покрытия тестов `pytest` в
`pyproject.toml`.

Action тоже не роняет джоб из-за того, что сдвинулось, но даёт workflow,
которому нужен свой gate, выходы, отличающие изменение от шума: см.
[Изменение или шум](#изменение-или-шум).

## В CI

В CI прогоняют `echolot doctor -q`, затем `analyze` и `compare` с последним
успешным отчётом базовой ветки, сохраняя отчёты как артефакты.

### GitHub Action

`action.yml` в корне репозитория делает всё за один шаг после бенчмарка:

```yaml
permissions:
  contents: read
  actions: read            # чтобы скачать отчёт последнего успешного прогона

steps:
  # … checkout, запуск устройства, запуск бенчмарка …
  - uses: grishan0v/echolot@v0.18.0
    with:
      traces: app/benchmark/build/outputs/**/StartupBenchmark_startup_iter*.perfetto-trace
```

Action устанавливает `echolot` указанного тега (или `@main`), кэширует
`trace_processor`, проверяет раннер через `echolot doctor -q`, запускает
`analyze`, скачивает базовый `report.json` с базовой ветки/workflow, строит
`compare` и публикует сводку в Job Summary (и при `comment: true` — в
комментарий PR).

| вход | по умолчанию | назначение |
|---|---|---|
| `traces` | — | пути или glob-шаблоны к трейсам одного теста |
| `config` | `echolot.yml` | конфиг проекта |
| `scenario` | первый в конфиге | сценарий из `scenarios:` |
| `baseline` | — | явный `report.json` вместо поиска по артефактам |
| `baseline-branch` | base / default branch | ветка для поиска базового отчёта |
| `baseline-workflow` | текущий workflow | файл workflow с базовыми отчётами |
| `artifact-name` | `echolot-report` | имя артефакта |
| `comment` | `false` | публиковать и обновлять комментарий в PR |
| `python` | `python3` | интерпретатор Python ≥3.10 |
| `token` | токен джоба | токен для чтения артефактов и комментариев |

Выходы:

- `report`, `baseline`, `comparison` — пути к `report.json` этого прогона,
  к базовому отчёту и к `comparison.json`;
- `moved` — сколько строк выросло или уменьшилось выше порога шума;
  `appeared` и `vanished` — сколько появилось и пропало, отдельно от `moved`;
- `held` — сколько из строк `moved` ещё и держится (столбец Holds: «да»);
- `held-rows` — первые пять из них в порядке сравнения, JSON-массивом:
  `detector`, `location`, `detail` (если у детектора он есть), `delta_ms`,
  границы интервала `low_ms` и `high_ms`, `floor_ms` — порог, за который
  они вышли, `on_main`;
- `verdict` — вердикт простого чтения по окну сценария: `better`, `worse`,
  `no_change` или `not_compared`; `headline` — он же словами, например
  `Slower by 1.2 s`;
- `window-delta-ms` — на сколько сдвинулось окно, «после» минус «до», в мс;
- `window-holds` — `true` или `false`: держится ли этот сдвиг, как у строки
  ([окно и старт](#окно-и-старт)); пусто, если прогонов мало или отчёт не
  хранит окна по прогонам;
- `comparable` — `false`, если отчёты не об одном: два процесса, два окна
  или якорь, который не нашёл ни один прогон;
- `warnings` — id предупреждений сравнения через запятую, например
  `drift,runs`;
- `unlike` — те из них, что говорят: стороны записаны или прочитаны не
  одинаково (скорость или нагрев телефона, конфиг, пороги, запись,
  компиляция, версия echolot), — то, что простое чтение перечисляет в
  «Not recorded alike».

Все, кроме первого, пусты, когда сравнивать не с чем. Читаются они из
`comparison.json`, а не из текста таблицы. `.github/workflows/action.yml`
проверяет их на демо: в заложенном изменении две строки блокировки
сдвигаются и держатся, а запуск, длиннее на 2%, — `no_change`, и его сдвиг
не держится.

### Изменение или шум

`moved` считает всё, что выше порога, а порог — не проверка: одна сборка
против самой себя (два набора по 15 холодных стартов большого приложения,
поделённые 7 на 8 по-разному) дала `moved` от 48 до 73, и столько же
`appeared` и `vanished`. `held` на тех же парах — от 1 до 12, пока Holds
спрашивал только про ноль, больше всего при делении по времени, где
[дрейф](#повторы-которые-дрейфуют) набора сказывается целиком; против порога
строки — от 0 до 4. Вердикт грубее всех и устойчивее всех: на 1 479 парах
неизменённых наборов он не сдвинулся ни разу. Сколько строк держит пара вашего
сценария сама по себе, когда ничего не менялось, меряет `analyze --noise` на
наборе базовой ветки (см. [Собственный шум сценария](#собственный-шум-сценария)).

Сам Action не роняет джоб из-за сдвигов. Workflow, которому нужен свой gate,
строит его отдельным шагом:

```yaml
  - uses: grishan0v/echolot@v0.18.0
    id: echolot
    with:
      traces: app/benchmark/build/outputs/**/StartupBenchmark_startup_iter*.perfetto-trace

  # Правило проекта: запуск медленнее при сторонах, записанных одинаково,
  # и без дрейфа ни в одной, останавливает сборку.
  - name: Stop on a slower launch
    if: >-
      steps.echolot.outputs.verdict == 'worse'
      && steps.echolot.outputs.unlike == ''
      && !contains(steps.echolot.outputs.warnings, 'drift')
    env:
      HEADLINE: ${{ steps.echolot.outputs.headline }}
      HELD_ROWS: ${{ steps.echolot.outputs.held-rows }}
    run: |
      echo "::error title=echolot::$HEADLINE"
      echo "$HELD_ROWS" | jq -r '.[] | "\(.delta_ms) ms (\(.low_ms) to \(.high_ms))  \(.detector)  \(.location)"'
      exit 1
```

`worse` уже означает, что отчёты сравнимы: несравнимая пара получает
`not_compared`. `no_change` при строках, которые держатся, как на демо, —
изменение внутри запуска, не удлинившее его на пятую часть; останавливать ли
на нём сборку — решение проекта, и для этого есть `held`.

### Несколько сценариев

Если в конфиге несколько сценариев, каждый запускается отдельным шагом или
ногой матрицы со своим `scenario` и своим `artifact-name`:

```yaml
jobs:
  benchmark:
    runs-on: ubuntu-latest
    strategy:
      matrix:
        include:
          - scenario: coldStart
            test: StartupBenchmark_startup
          - scenario: feed_scroll
            test: ScrollBenchmark_feed
    steps:
      # … checkout, устройство, запуск ${{ matrix.test }} …
      - uses: grishan0v/echolot@v0.18.0
        with:
          traces: app/benchmark/build/outputs/**/${{ matrix.test }}_iter*.perfetto-trace
          scenario: ${{ matrix.scenario }}
          artifact-name: echolot-${{ matrix.scenario }}
```
