# Планирование

[← Оглавление](README.md) · [README](../../README.ru.md) · [English](../planning.md) · **Русский**

Каждое улучшение и каждый баг — это GitHub issue, и каждое открытое issue
является карточкой на доске
[Echolot Roadmap](https://github.com/users/grishan0v/projects/1). Никаких
других списков нет. План в локальном файле не виден никому другому и
незаметно устаревает.

Доска публичная: любой может увидеть, что запланировано и в каком порядке.
Перечисленные ниже поля выставляет мейнтейнер инструмента.

## Создание issue

Сырую идею можно начать в
[Discussions → Ideas](https://github.com/grishan0v/echolot/discussions/categories/ideas).
Когда становится понятно, что нужно делать, она оформляется в issue, а в тред
добавляется ссылка на него.

Открывайте issue по шаблону: **Feature request** для улучшения, **Bug report**
для бага. Шаблон сам выставляет метку; issue только про документацию берёт
`documentation`. Разделы шаблона фичи — проблема, предложение, альтернативы,
влияние на детерминизм — используются потом для сортировки, так что
заполненный шаблон — это большая часть работы.

Перед созданием:

- **Поищите среди открытых issue.** Если такая идея уже есть, лучше оставить
  комментарий там.
- **Сверьтесь с принятыми в репозитории решениями.** Чаще всего всплывают:
  [Почему на производительности намеренно нет gate](compare.md#почему-в-ci-намеренно-нет-gate),
  [Почему CLI, а не MCP-сервер](agent-layer.md#почему-cli-а-не-mcp-сервер) и
  [главное правило](../../echolot/guide/overview.md#the-one-rule): никогда не
  открывать трейс напрямую. Идея, противоречащая одному из них, либо
  перерабатывается под него, либо закрывается с указанием причины.
  [#134](https://github.com/grishan0v/echolot/issues/134) пошло по первому
  пути, [#137](https://github.com/grishan0v/echolot/issues/137) — по второму.
- **Не упоминайте реальные проекты.** Репозиторий публичный. Для примера нужна
  форма проблемы, а она одинакова под любым именем: `com.example.app`, `Store`,
  `collection_load` ([#105](https://github.com/grishan0v/echolot/pull/105)).
- **Пишите на английском**, как и всё остальное в трекере и коде.

## Четыре поля

Кроме Status, у каждой карточки есть четыре поля. Определения ниже совпадают с
описаниями опций на самой доске, чтобы они были перед глазами при разборе.

### Area: какая часть инструмента меняется

| опция | что охватывает |
|---|---|
| Core | что инструмент находит и насколько точно: запись, детекторы, статистика, `compare` |
| UX | как с ним работает человек или агент: команды, конфиг, вывод, скорость цикла поиска |
| Integrations | как инструмент доходит до людей и их систем: плагин, CI, другие клиенты |
| Health | то, что не видно пользователям: структура кода, документация, приватность |

Area удерживает баланс работ и не влияет на приоритет.

### Value: насколько это нужно

Решает один вопрос: насколько хуже пользователю или мейнтейнеру, если этого
не сделать никогда?

| опция | если не делать никогда |
|---|---|
| High | инструмент даёт неверный ответ, пропускает то, что должен найти, или что-то утекает |
| Medium | ответ приходит медленнее или менее ясно, инструмент охватывает меньше людей, или следующие изменения в этом месте становятся дорогими |
| Low | удобство, отсутствия которого пока никто не заметил |

Между двумя задачами одинаковой Value первой идёт та, что проявилась на
реальных прогонах.

### Effort: размер реализации

| опция | размер |
|---|---|
| S | до одного дня: один модуль, один PR |
| M | несколько дней: несколько модулей, новое поле отчёта, документация и self-check |
| L | неделя и больше, или новая зависимость |

Задача размера L разбивается на подзадачи S и M до начала работы — через
**Create sub-issue** на странице родителя. Родитель оставляет Area и Value, а
Effort и Readiness остаются пустыми, так как их несут подзадачи. Так устроена
[#142](https://github.com/grishan0v/echolot/issues/142).

### Readiness: можно ли делать сейчас

| опция | значение |
|---|---|
| Ready | понятно, что и как делать, ничто не блокирует |
| Spike | сначала нужна проверка |
| Waiting | блокируется чем-то извне: данными, устройством, другой задачей |

Тест на spike: есть ли открытый вопрос, ответ на который может отменить issue
или изменить его размер больше чем на шаг? Если да — это Spike. Если нет — это
Ready, а оставшиеся детали решаются по ходу реализации.

Spike — это проверка на один-два дня: на устройстве, на реальных трейсах или
на прототипе. Поля Effort у него нет. Он завершается комментарием с ответом, и
далее происходит одно из двух: выставляется Effort и Readiness меняется на
Ready, либо issue закрывается с этим ответом в качестве причины.

## Выбор следующей задачи

1. Ready и High, начиная с наименьшего Effort.
2. Параллельно — spike-и с High Value: там, где от самой нужной работы
   неизвестен исход, проверка окупается сильнее всего.
3. L разбивается на подзадачи до старта.
4. Low вместе с L — кандидат на закрытие как «not planned».
5. Раз в месяц — смотреть распределение открытых задач по Area, чтобы Health
   не ждал вечно.

Порядок нигде не хранится вручную — он следует из полей.

## От карточки до Done

Доска двигает карточки сама:

| событие | действие доски |
|---|---|
| issue добавлено на доску | ставит Status в Todo |
| у issue на доске появились подзадачи | добавляет их на доску |
| к issue привязан PR | ставит Status в In Progress |
| issue закрыто | ставит Status в Done |
| карточка перенесена в Done | закрывает issue |

Вручную нужна только привязка. В описании PR, закрывающего issue, пишется
`Closes #N`: открытие переводит карточку в In Progress, а слияние закрывает
issue и переносит карточку в Done.

Задача, которую делать не будут, закрывается как «not planned» с комментарием о
причине — чтобы следующий человек с той же идеей сразу увидел ответ — и её
карточка архивируется с доски.

## Из командной строки

Те же шаги через `gh`. Токену нужен скоуп `project`:
`gh auth refresh -s project`.

```bash
gh issue create --title "[Feature]: …" --label enhancement --body-file issue.md
gh project item-add 1 --owner grishan0v --url <issue URL>

# идентификаторы, которые запрашивает item-edit
gh project view 1 --owner grishan0v --format json --jq .id    # доска
gh project item-list 1 --owner grishan0v --format json --limit 1000   # карточки
gh project field-list 1 --owner grishan0v --format json        # поля и опции
gh project item-edit --project-id <board id> --id <card id> \
  --field-id <field id> --single-select-option-id <option id>

gh issue close <N> --reason "not planned" --comment "почему"
gh project item-archive 1 --owner grishan0v --id <card id>
```
