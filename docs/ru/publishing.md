# Публикация на PyPI

[← Оглавление](README.md) · [README](../../README.ru.md) · [English](../publishing.md) · **Русский**

Релиз — это git-тег. Workflow `.github/workflows/publish.yml` по тегу собирает
`sdist` и `wheel`, загружает их через PyPI Trusted Publishing — без хранения
API-токенов в репозитории или секретах GitHub — и затем создаёт GitHub Release
для этого тега: прикрепляет оба файла, группирует список PR со времени прошлого
тега по типу изменений и добавляет сверху ссылку на версию на PyPI. GitHub
Release создаётся только после успешной загрузки на PyPI, поэтому оба ресурса
всегда согласованы.

## Разовая настройка на PyPI

Она была выполнена ещё до первого релиза. Проект уже опубликован под именем
`echolot`, а окружение `pypi` настроено для Trusted Publishing. Если издателя
когда-нибудь понадобится пересоздать, укажите следующие значения:

1. Войдите на <https://pypi.org> и откройте
   <https://pypi.org/manage/project/echolot/settings/publishing/>. Издатель
   существующего проекта настраивается на странице самого проекта; раздел
   pending publishers в настройках аккаунта предназначен для имён, которые ещё
   никто не публиковал.
2. В разделе **Add a new publisher → GitHub** заполните:

   | поле | значение |
   |---|---|
   | Owner | `grishan0v` |
   | Repository name | `echolot` |
   | Workflow name | `publish.yml` |
   | Environment name | `pypi` |

   Имя окружения должно совпадать с `environment: name:` в workflow. GitHub
   создаёт окружение при первом запуске, и здесь у него нет правил защиты —
   дополнительно настраивать ничего не нужно. Добавленное позже правило вроде
   обязательного ревьюера или таймера ожидания останавливало бы загрузку на
   каждом теге.

## Перед релизом: что уже проверил CI

`.github/workflows/checks.yml` запускается на каждом PR в `main` и на самом
`main` после слияния: `pytest` с порогом покрытия — на Python 3.10 и 3.14 для
PR и на всех пяти заявленных в classifiers версиях для `main`;
`ruff check echolot tests action` рядом с `pytest` на 3.14; и job `package`,
который проверяет README тремя способами, собирает артефакты и устанавливает их.
Набор правил `protect-main` требует перед слиянием прохождения двух проверок:
`checks` (проходит только если прошли все запущенные версии Python и линтер) и
`package`. Поломка, затрагивающая только 3.11, 3.12 или 3.13, проявится на
`main` после слияния, поэтому посмотрите на этот прогон перед тем, как ставить
тег.

Перед релизом особенно важен job `package`, потому что номер версии на PyPI
нельзя использовать повторно — даже после удаления. Ошибка, найденная на теге,
стоит номера версии; та же ошибка, пойманная на PR, стоит одного коммита.

Что именно он проверяет и зачем каждая проверка отдельно:

| шаг | что без него попало бы на PyPI |
|---|---|
| сравнение бейджа версии с classifiers | главная страница, заявляющая версии Python, на которых ничего не проверялось |
| `readme_renderer` для `README.md` | адреса картинок, вырезанные санитайзером и превратившиеся в пустые рамки |
| отсутствие относительных ссылок в `README.md` | ссылки, ведущие на несуществующие адреса `pypi.org` (404) |
| `python -m build` и `twine check` | сломанные метаданные пакета |
| установка `sdist` и `wheel` в чистые окружения и запуск вне исходников: подсчёт файлов пакета, `echolot --help` и `doctor -q` | пакет без детекторов, гайдов или слоя `.claude/` — `package-data`, который editable-установка не проверяет |

**`twine check` не проверяет рендер.** Для Markdown README он вообще не
открывает файл: его таблица `_RENDERERS` сопоставляет `text/markdown` с `None`
с комментарием «Rendering cannot fail». Он проверяет только метаданные пакета.
Рендер выполняется отдельным шагом с предварительной установкой
`readme_renderer[md]`, так как поддержка Markdown — это опциональная
зависимость, которую не ставят ни `twine`, ни сам `readme_renderer`.

Эта разница стоила четырёх релизов: бейдж лицензии указывал на относительный
путь `LICENSE`, который на `pypi.org` ведёт в никуда, и при этом все сборки
оставались зелёными.

## Выпуск релиза

Поднятие версии идёт через обычный PR, так как `protect-main` требует PR для
любых изменений в `main`. Тег ставится потом на слитый коммит.

```bash
# 1. В ветке обновите __version__ в echolot/__init__.py, "version" в
#    plugins/echolot/.claude-plugin/plugin.json и в
#    plugins/echolot/.cursor-plugin/plugin.json, а также "ref" в
#    .claude-plugin/marketplace.json ("v" + версия) и откройте PR в main
#    (pyproject.toml читает версию из этого атрибута; tests/test_plugin.py
#    упадёт, пока все четыре не совпадут). Начиная с 0.10.0 строки action
#    `uses: grishan0v/echolot@...` в README*.md и docs/**/compare.md
#    должны указывать на тот же тег; tests/test_action.py проверяет их
# 2. После слияния поставьте тег на слитый коммит — тег обязан быть "v" + версия,
#    workflow проверяет это
git switch main && git pull
git tag vX.Y.Z
git push origin vX.Y.Z
```

Следите за прогоном во вкладке **Actions**. Когда он станет зелёным, пакет
появится на <https://pypi.org/project/echolot/>, заработает
`pipx install echolot`, а релиз отобразится на
<https://github.com/grishan0v/echolot/releases>. Сгенерированные заметки
перечисляют PR с прошлого тега по заголовкам в разделах
[ниже](#как-группируются-заметки-к-релизу) — при необходимости дополните их
вручную через интерфейс GitHub.

Этот же тег выпускает и плагин. Запись в маркетплейсе забирает
`plugins/echolot` по этому тегу, поэтому до пуша тега она указывает на ещё не
существующий тег и установка падает — пушьте тег сразу после слияния.

Он же выпускает GitHub Action: `uses: grishan0v/echolot@vX.Y.Z` ставит
`echolot` этого тега из собственного чекаута action, так что action и CLI
всегда одной версии.

Пакет на PyPI тоже содержит плагин: `setup.py` копирует `plugins/echolot` в
`wheel` как `echolot/plugin`, а `MANIFEST.in` включает его в `sdist`;
`echolot plugin cursor` копирует его в Cursor. Отдельно для Cursor ничего
выпускать не нужно: версия в его манифесте обновляется вместе с остальными, и
smoke-тест в `checks.yml` упадёт, если `wheel` или `sdist` соберётся без
плагина.

Каталог сообщества Cursor (`cursor.directory`) хранит собственную копию
плагина: текст и описания каждого скилла на момент отправки заявки 2026-10-15
(версия 0.15.0). Теги туда не попадают, и автоматической синхронизации с
репозиторием нет. Если релиз меняет файл в `plugins/echolot/skills/`,
обновите скилл в форме редактирования
<https://cursor.directory/plugins/echolot/edit> под аккаунтом автора: тело
`SKILL.md` ниже frontmatter вставляется в Content, а `description` из
frontmatter — в Description. После правки текста карточка скрывается до
повторного прохождения проверки безопасности сайта.

Тег и релиз — это снимок: он включает только то, что было закоммичено до
создания тега. Чтобы выпустить исправление, поднимите версию в новом PR и
поставьте новый тег — уже загруженный номер версии нельзя использовать на PyPI
повторно даже после удаления.

## Как группируются заметки к релизу

Заметки генерирует GitHub, а `.github/release.yml` задаёт секции: PR попадает
в первую подходящую секцию по своим меткам.

| секция | метка | кто ставит |
|---|---|---|
| Detectors | `detector` | изменение файла в `echolot/sql/detectors/` |
| Features | `enhancement` | заголовок начинается с `feat:` или `perf:` |
| Fixes | `bug` | `fix:` |
| Documentation | `documentation` | `docs:` |
| Maintenance | `maintenance`, `dependencies`, `github_actions` | `build:`, `chore:`, `ci:`, `refactor:`, `style:`, `test:`; остальные две ставит dependabot на свои PR |
| Other | любая другая | заголовок без одного из этих типов |

`.github/workflows/labels.yml` проставляет метки при открытии PR, при изменении
его заголовка и ещё раз при слиянии: итоговый список файлов решает судьбу метки
`detector`. У типа может быть scope и `!`: `fix(report): …`, `feat!: …`.
Исправление заголовка с `feat:` на `fix:` переносит PR из Features в Fixes.
Заголовок без известного префикса не получает автоматической метки, а метки,
поставленные вручную, сохраняются.

Метка `detector` ставится и остаётся навсегда. Исправление детектора попадает
в Detectors, потому что меняет ответ отчёта на одном и том же трейсе — а именно
это важнее всего знать читателю заметок к релизу.

Documentation — это `docs/` и README. `echolot/guide/` и `echolot/claude/`
читает агент, и они поставляются внутри пакета, поэтому изменения в них — это
фича или фикс.

PR в неверной секции исправляется до тега — правкой заголовка или метки. После
тега — правкой заметок релиза в UI GitHub.

Workflow запускается на `pull_request_target`, поэтому PR из форков и от
dependabot тоже получают метки. Токен этого триггера имеет права на запись,
поэтому workflow читает только заголовок и список файлов и никогда не делает
checkout кода PR; `tests/test_release_notes.py` гарантирует это. Метки не
выбирают тип версии: решение о minor или patch обосновывается в PR с поднятием
версии.

## Локальная проверка артефактов

Упаковочная часть job `package`, полезная перед простановкой тега. CI уже
прогнал все пять проверок на PR, так что это контрольный просмотр, а не
единственный барьер.

```bash
python -m pip install --upgrade build twine
rm -rf dist && python -m build
python -m twine check dist/*
```

Это проверяет метаданные пакета и для Markdown README больше ничего не делает —
подробности выше. `readme_renderer` ставится как зависимость `twine`, но без
дополнения `[md]` его Markdown-рендерер возвращает `None` вместо HTML, поэтому
workflow предварительно ставит `readme_renderer[md]`.

Три проверки README здесь не дублируются: каждая занимает десяток строк Python
в `checks.yml`, и вторая копия разошлась бы с первой за пару релизов. Они
покрывают бейдж версии против classifiers, сохранность URL картинок после
санитайзера PyPI и отсутствие относительных ссылок — которые ведут на
`pypi.org`, из-за чего README использует полные ссылки на GitHub, а `docs/*.md`
ссылаются друг на друга относительно.

## Ручная загрузка при необходимости

Штатный путь — Trusted Publishing. Если загрузить релиз нужно вручную (сломан
workflow или тестируется аккаунт), создайте API-токен на
<https://pypi.org/manage/account/token/> и выполните:

```bash
python -m twine upload dist/*
# username: __token__
# password: ваш токен
```

Когда проект уже существует, ограничьте область действия токена только этим
проектом.
