# Детекторы

[← Оглавление](README.md) · [README](../../README.ru.md) · [English](../detectors.md) · **Русский**

Детектор — это один самодостаточный `.sql`-файл. Метаданные в шапке,
плейсхолдеры `{{param}}` подставляются из конфига:

```sql
-- @id: my_detector
-- @title: What we are looking for
-- @why: why it matters
-- @param: threshold_ms = 50 ms — how long one slice has to take to count
-- @identity: location, detail
-- @column: location — the slice name
-- @column: count — its slices that took the threshold or longer
-- @column: total_ms — their time, summed
-- @column: max_ms — the longest one
-- @column: detail — the thread they ran on
-- @plain_title: Work that takes long
-- @plain_why: One or two plain sentences on how it touches the app.
-- @plain_clean: What a result with nothing in it says.

SELECT name AS location, COUNT(*) AS count,
       ROUND(SUM(dur)/1e6, 2) AS total_ms,
       ROUND(MAX(dur)/1e6, 2) AS max_ms,
       thread_name AS detail
FROM _slice_win
WHERE dur >= {{threshold_ms}} * 1000000
GROUP BY name, thread_name
ORDER BY total_ms DESC
LIMIT 20;
```

Положите файл в `echolot/sql/detectors/` — и он сразу начнёт выполняться.
Регистрация в коде не нужна, а `@param` задаёт значения по умолчанию. Для
полноценного включения в поставку нужен ещё чек-лист ниже
([Добавление детектора](#добавление-детектора)).

Контракт столбцов общий: `location`, `count`, `self_ms`, `total_ms`,
`max_ms`, `covered_ms`, `detail`. Детектор, группирующий по имени потока,
заполняет ещё `threads` — сколько потоков сложено в строке: ядро обрезает имя
до 15 символов, и потоки пула приходят под одним. Где главный поток отличён
по tid, его строка называется `main`; при слиянии повторов `threads` берётся
наибольшим из найденных. `@identity` перечисляет столбцы
группировки (по умолчанию `location`, обязательно включает его). В
идентичность нельзя включать поля, меняющиеся от прогона к прогону: иначе
`analyze` и `compare` не смогут свернуть и сопоставить повторы.

Что значат параметр и столбец, тоже пишется в шапке: имя этого не говорит.
`max_total_ms` у `binder_txn` — нижняя граница, а `max_ms` у `frame_jank` —
опоздание кадра относительно дедлайна, а не его длительность. В `@param` за
числом идёт единица, за строкой — ничего, а пояснение — после тире и, если
нужно, на следующих строках. `@column` — по строке на каждый столбец запроса,
после `@identity` и до ключей `@plain_*`:

```sql
-- @param: min_overrun_ms = 4 ms — how far past its deadline a frame has to
--       finish to count as late at all
-- @param: name_glob = *GC — GLOB over slice names: ART's collection cycles
-- @column: max_ms — the worst frame's overrun past its deadline
```

Это печатает `echolot explain <детектор>` вместе со значением каждого порога
в этом проекте, так что пояснения живут только в шапке.

`@needs` указывает, какие данные должны присутствовать в трейсе (ставится
сразу после блока `@why`). `@plain_title`, `@plain_why`, `@plain_clean`
задают человекочитаемые тексты для `echolot report --plain` и `report.html`
(должны быть последними ключами шапки, за ними — пустая строка `--`).

## Контекстные представления

Представления уже отфильтрованы по нужному процессу и окну сценария:

| представление | что внутри |
|---|---|
| `_proc` | целевой процесс (ровно один) |
| `_slice` | все **потоковые** срезы процесса с флагом `is_main_thread` |
| `_aslice` | **async**-секции процесса (`Trace.beginAsyncSection`) |
| `_anchor` | `_slice` и `_aslice` вместе — только имя и время для якорей |
| `_window` | границы `ts_start` / `ts_end` окна сценария |
| `_slice_win` | потоковые срезы, **пересекающиеся** с окном |
| `_aslice_win` | async-секции, **пересекающиеся** с окном |
| `_tstate_win` | состояния потоков, **обрезанные** по окну |
| `_cpu_in_slice` | время на CPU внутри срезов верхнего уровня |
| `_samples_by_slice` | сэмплы стеков вызовов в окне с привязкой к срезам |
| `_claimed_name` | имена срезов, уже охваченные масками `*name_glob*` |
| `_sched_win` | что выполнялось на каждом CPU (`app`, `other`, `idle`) |
| `_main_runnable_held` | ожидания CPU главным потоком в разрезе того, что занимало ядро |
| `_main_runnable_idle` | те же ожидания относительно простоя других ядер |

### Два столбца длительности — не дублирование

`_slice_win` содержит оба: `dur` (полная длина среза для показа человеку) и
`dur_win` (часть внутри окна — для подсчёта долей и покрытия).

### Незакрытый срез — самый долгий, а не нулевой

`trace_processor` выставляет `dur = -1` срезам, не закрытым к концу записи.
`_slice_win` продлевает их до конца окна и помечает флагом `unfinished`.
Аналогично обрабатываются незакрытый конечный якорь, последнее состояние
потока и открытые дочерние срезы.

### Отрезки и исключения из правил

- **`anr_risk`** ищет непрерывные участки без возврата главного потока в
  очередь сообщений на глубине 1 и ниже (глубина 0 намеренно исключена, так
  как там лежат якоря сценария вроде `AppStart`).
- **`anr`** — единственный детектор, не обрезаемый окном сценария (ANR может
  зафиксироваться спустя 5 с после закрытия окна старта).
- Внешние stdlib-модули Perfetto объявляются в шапке через
  `-- @module: android.anrs`.
- Для единичных выбросов вместо сумм используйте оконные функции SQLite 3.50
  (`ROW_NUMBER() OVER ...`), как в `main_thread_outlier`.
- Не переписывайте пересечение интервалов вручную через `JOIN ... ON`:
  используйте готовое представление `_cpu_in_slice` на базе `SPAN_JOIN`.
- Границы окна `ts_start` / `ts_end` подставляются литералами, а не
  вычисляемым view, чтобы избежать деградации производительности на больших
  трейсах.
- По той же причине `_slice`, `_slice_win`, `_child_sum`, `_aslice_win` и
  `_tstate_win` — `PERFETTO TABLE`, а не view: строятся один раз, и детектор
  читает сохранённые строки, а не пересчитывает join под ними при каждой
  ссылке. Таблица удаляется через `DROP TABLE IF EXISTS`, view — через
  `DROP VIEW IF EXISTS`; `doctor` прогоняет скрипты дважды в одной сессии и
  держит их к этому.
- `_slice_win` проиндексирована по `slice_id`. View над `slice` отдавал join
  по id собственному поиску `slice`, а у таблицы его нет, пока его не создать.
  Без индекса обход дерева androidx.startup в `app_init`, который на каждом
  шаге соединяет `_slice_win` по id каждого потомка, читал всё окно на каждую
  строку: 2,5 с на запрос на одном холодном старте, три запроса на трейс
  набора — три четверти времени трейса.

## Self time против total time

`main_thread_block` считает **self** time (время среза минус время детей),
чтобы не считать вложенные уровни вроде `Choreographer#doFrame` → `traversal`
→ `draw` трижды. При этом `total_ms` выводится в соседнем столбце.

## Два условия вместо одного

Многие детекторы срабатывают либо на один долгий вызов, **либо** на
накопленную сумму множества мелких (например, 76 binder-вызовов по 9 мс).

## Какое время покрывают строки (`-- @intervals`)

Вторая часть запроса после `-- @intervals` возвращает интервалы `(ts, dur)`
на главном потоке, стоящие за строками `_rows`, чтобы в шапке отчёта
корректно посчитать процент окна **Covered by the findings below** без
двойного учёта перекрытий. Детекторы не про главный поток (`frame_jank`,
`anr`) возвращают пустой результат.

## Что там выполнялось (`-- @samples`)

Третья секция после `-- @samples` связывает строки из `_rows` с
`callsite_id` из `_samples_by_slice`, а `echolot/stacks.py` вытаскивает
верхний осмысленный метод и ближайший фрейм проекта.

## На чём часто спотыкаются

1. **`SPAN_JOIN` не ругается на перекрывающиеся интервалы внутри партиции** —
   он молча считает их дважды. Всегда гарантируйте непересекаемость входных
   таблиц по ключу партиционирования.
2. **Проверяйте реальную схему `trace_processor`** (`SELECT * FROM … LIMIT 1`),
   а не угадывайте имена колонок и единицы измерения (температура приходит в
   миллиградусах, meminfo — в байтах).
3. **Будивший поток (`waker_utid`) записан на состоянии после сна** (на
   последующем `R`, читается через `LEAD`), а не на самом сне.
4. **Запрос должен переживать повторный запуск** в одной сессии — ставьте
   `DROP VIEW IF EXISTS` / `DROP TABLE IF EXISTS`.

## Когда в трейсе нет данных для детектора

Указанный в `-- @needs:` источник проверяется при анализе. Поддерживаются:
`platform_state`, `frame_timeline`, `composable_names`, `atrace:am`,
`atrace:dalvik`, `atrace:binder_driver`. Если нужных данных не было,
`report.json` фиксирует `checked: false` и `reason`, `report.md` переносит
детектор в верхнее предупреждение, а `compare` исключает его из сравнения.

## Добавление детектора

Чтобы новый `.sql` стал штатным детектором, помимо самого файла нужны:

1. Проблема в `echolot/fixture.py` (или явное включение в `SILENT_ON_FIXTURE`
   в `echolot/selftest.py`) и проверки в `selftest.py`.
2. Обновление README и графиков: `DETECTOR_ORDER` (и переводы в
   `docs/languages.yml`), затем `python docs/assets/render.py`, чтобы
   обновить счётчик детекторов, пример отчёта и SVG-таблицы.
3. Секция `-- @intervals` и `LIMIT` в основном запросе (`tests/test_in_rows.py`).
4. Поля `@plain_title`, `@plain_why`, `@plain_clean` и шаблон в
   `echolot/plain.py` (`tests/test_plain.py`, `tests/test_report_page.py`);
   пояснение и единица у каждого `@param` и строка `@column` на каждый
   столбец запроса (`tests/test_explain.py` и проверка `doctor`, что строки
   несут ровно те столбцы, которые объясняет шапка).
5. Соблюдение контракта слияния (`@identity`, метрики, `detail`), типов
   `@param`, `@needs` (`tests/test_needs.py`) и соглашений имён масок
   (`*name_glob*`, `skip_glob`).

## Устойчивость к ошибкам

Ошибка в одном детекторе никогда не роняет весь прогон: текст ошибки пишется
в stderr и `report.json`, а остальные детекторы продолжают работу.
