# `mark`: первые маркеры из словаря платформы

[← Оглавление](README.md) · [README](../../README.ru.md) · [English](../mark.md) · **Русский**

```bash
echolot mark                     # куда поставить первые маркеры и почему туда
echolot mark --apply             # вставить применимые автоматически
./gradlew :app:installBenchmark  # режимы launch и command: задача, которую назовёт --apply
echolot collect -c echolot.yml -n 3 && echolot analyze .echolot/traces/coldStart_iter*.perfetto-trace -c echolot.yml
echolot mark --remove            # удалить все маркеры с точностью до байта
```

## Какую проблему решает

Проект без инструментирования не даёт детекторам ни одного имени из кода
приложения. `main_thread_block` говорит `bindApplication`, `activityStart`,
`Compose:recompose`; `uninstrumented_cpu` говорит, что `arch_disk_io_0..3`
сожгли 900 мс. Это факты, но ни один из них не является файлом. `domains`
нечего сопоставить, и следующий шаг агента — добавить маркеры `AGENTTMP_` и
перезаписать трейс — требует понимать, куда их ставить. В двух расследованиях
из двух агент искал эти места чтением приложения: пара десятков вызовов `cat`
и `sed -n`, от 40% до 60% всего контекстного окна, ещё до постановки первого
маркера.

`mark` автоматизирует этот шаг. Команда отвечает: «куда поставить пять–семь
маркеров, чтобы следующий отчёт назвал код именно этого приложения» — и
отвечает одинаково на любом проекте, а это единственная форма, допустимая для
инструмента, обещающего детерминированный результат.

## К чему привязывается и что пропускает

Всё, на что смотрит `mark`, задано платформой или библиотеками, а не
соглашениями проекта. Каждая строка вывода помечается одним из тегов:

| тег | что это | пример |
|---|---|---|
| `manifest+lifecycle` | манифест называет класс — launcher Activity имеет `<intent-filter>` с `MAIN` и `LAUNCHER`, класс Application задан через `android:name` в `<application>` — а метод SDK `onCreate` указывает точку внутри него независимо от имени класса | `override fun onCreate(`, `protected void onCreate(` |
| `api` | точные вызовы популярных библиотек | `setContent {`, `setContentView(`, `Room.databaseBuilder(`, `startKoin {` |
| `call-from-setContent` | composable-функции внутри `setContent { }`, только если `@Composable fun Name(` объявлена в исходниках этого проекта | `AppTheme { AppNavHost() }` → обе, если определены здесь |
| `anr` | фрейм стека из зависания с флагом `--from-anr`: функция вокруг строки из фрейма | см. `--from-anr` ниже |
| `jdk` | поток или пул со стандартным именем фабрики JDK, с флагом `--pools` | `Executors.newSingleThreadExecutor()`, `Thread(task)` |

Нет никаких правил про `*ViewModel`, `*Repository`, `*Screen`, `*Fragment` и
прочие соглашения об именовании. Проект с `Presenter` и `Page` получит
ровно тот же скелет маркеров, что и проект по гайдам Google — в self-check
собирается дерево с осмысленными именами и дерево с бессмысленными именами, и
требуется посимвольно одинаковый список предложений.

## Что сообщает, если не может найти

- нет `AndroidManifest.xml` с launcher-активностью под `src/main` — «no launcher
  Activity in any AndroidManifest.xml under src/main — this tree has no app
  entry point to mark», ничего не предлагается; `--root` указывает путь к
  приложению;
- два модуля с launcher-активностью (например, приложение и приложение для
  часов) — неоднозначность останавливает команду, пока `--module` или
  `project.package` не выберет один;
- две launcher-активности в одном манифесте — аналогичная остановка, так как
  `--module` выбирает модуль, а не точку входа внутри него; предложения
  выдаются для первой, для ручной разметки. `<activity-alias>` указывает на
  свою `targetActivity` и не считается второй активностью, а самозакрытый
  `<activity … />` не может содержать intent-filter;
- launcher Activity не переопределяет `onCreate` — об этом сообщается с
  указанием базового класса (`: Base()` в Kotlin, `extends Base` в Java), так
  как переопределение может быть там;
- класс Application отсутствует в манифесте или не переопределяет `onCreate` —
  сообщается, но при `bindApplication` всё равно видно, что выполняется:
  конструктор Application, ContentProvider-ы и инициализаторы библиотек,
  которые перечисляет `app_init`;
- класс Application с `@HiltAndroidApp` — выводится заметка без строки для
  разметки: граф генерируется, его стоимость видна внутри
  `Application.onCreate`, отдельно размечать нечего;
- блок, куда нельзя вставить пару целых строк begin/end — предлагается как
  неприменимый с указанием причины (случаи перечислены ниже);
- composable, builder Room, блок Koin — предлагаются с пояснением, почему не
  применяются автоматически (место вызова, цепочка билдера), и где обернуть
  вручную.

Каждая строка содержит путь к источнику. Вывод отсортирован по типу, пути и
строке и побайтово воспроизводим. Лимит — семь предложений (скелет, а не
полный обзор); количество сверх лимита печатается отдельно.

## `--apply` и `--remove`

`--apply` вставляет в каждое применимое место строку `beginSection` под
строкой с открывающей `{` блока и `endSection` над строкой с закрывающей `}`,
с отступом тела блока. В теле функции завершение заворачивается в `finally`,
чтобы секция закрывалась при любом выходе — `return`, `throw`, исключении из
вызова или после `while (true)`, где в Java голая строка в конце оказалась бы
недостижимой и сломала бы компиляцию. В лямбдах и composable-функциях
завершение ставится напрямую: компилятор Compose запрещает `try` вокруг
composable-вызовов.

```kotlin
override fun onCreate(savedInstanceState: Bundle?) {
    android.os.Trace.beginSection("AGENTTMP_activity_oncreate") // echolot:mark
    try { // echolot:mark
    super.onCreate(savedInstanceState)
    setContent {
        android.os.Trace.beginSection("AGENTTMP_set_content") // echolot:mark
        AppTheme { AppNavHost() }
        android.os.Trace.endSection() // echolot:mark
    }
    } finally { android.os.Trace.endSection() } // echolot:mark
}
```

`android.os.Trace` входит в фреймворк, никаких зависимостей добавлять не
нужно; каждая вставленная строка заканчивается на `// echolot:mark`; в Java
добавляется точка с запятой. Вставляются только целые строки между
существующими, с тем же окончанием строки (CRLF остаётся CRLF), больше в файле
ничего не меняется. `--remove` удаляет под `--root` именно строки с тегом в
формате `--apply` и возвращает каждый файл байт в байт: self-check применяет,
удаляет и сверяет, а `tests/test_mark_edits.py` проверяет то же на
сгенерированном Kotlin и Java, включая CRLF. Без `--root` корнем
считается исходный код проекта, как у `analyze`: `project.root`, иначе папка
конфига проекта — указанного в `-c`, иначе ближайшего `echolot.yml` от текущей
папки вверх до корня git-репозитория, так что `mark --remove` из `app/` или
соседнего модуля убирает то, что там же насчитал `hunt`, — иначе текущая папка. Строка с тегом в другом формате
содержит что-то ещё, поэтому не удаляется, а `--remove` выводит её файл и
номер строки для ручной очистки; так же её называют `echolot hunt`, его
проверка маркеров и страница в `echolot ui`, пока строка не исчезнет.
Повторный `--apply` ничего не дублирует: уже
размеченный блок пропускается с пометкой, а внешний блок вокруг размеченного
получит свою пару. `--remove` обходит все исходники под `--root`, включая
файлы вне `src/` (так как `--from-anr` размечает найденные фреймы). Ошибка
записи в файл выводится с продолжением работы. Скобки сопоставляются по копии
файла с вычищенными строками и комментариями, чтобы `}` внутри литерала не
сбила парсер.

Обещание не портить строки определяет случаи отказа. Блок предлагается, но
не применяется автоматически (с указанием причины), когда пару целых строк
нельзя вставить без правки существующей строки проекта:

- **`return` внутри лямбды или composable** — завершение без `try/finally`
  будет пропущено на раннем выходе;
- **файл в общем коде Kotlin** (`src/commonMain` и другие source set-ы кроме
  `androidMain`) — `android.os.Trace` там недоступен;
- **длина имени маркера больше 127 символов**, на которой `Trace.beginSection`
  падает во время записи — имя сгенерированного класса усекается, а если
  места не оставляет даже префикс, следует отказ;
- **весь блок в одну строку**, например `setContent { AppRoot() }` — между
  скобками нет отдельной строки;
- **код после `{` или перед `}` на той же строке**, например
  `setContent { AppTheme {` или `} }` — вставка потребовала бы разбить строку,
  а `--remove` только удаляет строки и не склеивает их обратно. Комментарий
  после `{` кодом не считается: строка `begin` встанет под ним.

Перенесите код на отдельную строку и снова запустите `mark`, или разметьте
вручную.

### Что дальше: сборка

`--apply` меняет только код, и последняя строка вывода подсказывает следующий
шаг. В режимах `launch` и `command` `collect` записывает сборку, уже
установленную на телефоне, и ничего не собирает сам — поэтому маркеры
попадут в трейс только после пересборки и установки. Вывод называет нужную
задачу Gradle, например `./gradlew :app:installBenchmark`, определяя по
скриптам сборки вариант с `project.package`. Если подходят два-три варианта,
перечисляются все. Если их больше трёх, называются варианты того build type,
на котором меряют, если таких не больше трёх; если и их больше или вариантов
нет вовсе — указывается имя пакета.
Debug-варианты не предлагаются никогда: они работают медленнее и иначе, чем
целевая сборка. Build type с `initWith` от debug наследует debuggable и тоже
исключается. Если модуль приложения применяет `androidx.baselineprofile`,
первым идёт `benchmarkRelease` этого плагина, а его `nonMinifiedRelease`,
собранный без R8 для генерации профилей, не предлагается никогда. В режиме
`gradle` приложение собирает и ставит сам
макроbenchmark, поэтому последняя строка предлагает сразу записывать. В
`--json` эта подсказка лежит в поле `next`.

Серия, записанная без пересборки, не содержит новых маркеров: `collect`
проверяет установленную сборку на их наличие перед записью и останавливается,
если чего-то не хватает (см.
[Сбор трейсов](collecting.md#сборка-на-телефоне)), а `analyze` предупреждает
об этом в шапке отчёта (см.
[Анализ](analysing.md#собственные-имена-измеряемые-каждый-раз)). После
`--remove` работает обратное: на телефоне ещё остаётся старая сборка с
маркерами, и `analyze` перечисляет те, что есть в трейсе, но уже удалены из
кода.

Учитывается `instrumentation.allowed` из `echolot.yml`, включая glob-шаблоны
по сегментам пути (например, `feature/*/src/main` покрывает все модули прямо
под `feature/`). Запись читается без `./` в начале, без `/` в конце и без
двойного `/`: `./app/src/main` — это `app/src/main`, а `.` — весь проект.
Пустой список разрешает любое место, и для `mark`, и для всех команд, которые
его читают. Точка вне списка всё равно показывается (с подсказкой
разметить ближайшего разрешённого вызывающего), но не применяется. Фрейм из
`--from-anr` и место из `--pools` вне разрешённых корней тоже помечаются как
находящиеся снаружи.

Конфиг берётся проектный: по флагу `-c`, иначе ближайший `echolot.yml` от
текущей папки вверх до корня git-репозитория, иначе из-под `--root`. Отсутствующий или битый конфиг при явном `-c` завершает
команду с кодом 2, кроме `--remove`: пустой `instrumentation.allowed`
разрешает всё, и ошибка в файле не должна мешать очистке. Без конфига `mark`
предупреждает в stderr, что ограничений на пути нет.

## `--from-anr`: цели из стека вместо манифеста

```bash
echolot mark --from-anr report.txt
```

Всё описанное выше предлагает точки, где инструментирование *обычно* нужно на
пустом проекте. Стек из ANR — не догадка: он называет методы, бывшие на
потоке при зависании, с файлом и строкой от компилятора. Дальнейший план, тег,
`--apply` и `--remove` работают точно так же.

Отчёт минифицированной сборки называет фреймы так, как их назвал R8,
`a.b.c(SourceFile:12)`, и ни один из них не совпадает с файлом чекаута, пока
mapping-файл сборки не вернёт имена: `--mapping app/build/outputs/mapping/release/mapping.txt`
или `project.mapping` из конфига, как у `anr`. Без них пустой план говорит,
сколько фреймов остались в именах R8 и чем их вернуть (в `--json` — `empty`).

Большинство предложений будут отклонены автоматически — читайте причины, а не
обходите их:

- **строка попала в другую функцию** — другая сборка, встроенная функция или
  сдвиг компилятора;
- **тело-выражение** — у `fun save(v: String) = …` нет блока, который можно
  обернуть: перепишите функцию с блоком или поставьте маркер в вызывающем коде;
- **`return` в теле**, **тело в одну строку**, **код на одной строке со
  скобкой** — те же отказы `--apply`, что и выше;
- **вход через лямбду** — `onCreate$lambda$0`,
  `Repo$refresh$1.invokeSuspend`, `lambda$flush$0` в javac. Лямбда часто
  выполняется позже создавшей её функции (слушатель клика, `launch`), так что
  маркер вокруг внешней функции измерил бы создание, а не вызов; размечайте
  внутри лямбды вручную;
- **`suspend fun`** — `beginSection`/`endSection` привязаны к текущему
  потоку, а корутина может возобновиться на другом потоке после `withContext`
  или `delay`; размечайте вручную участок без точек приостановки;
- **фрейм вне `instrumentation.allowed`** — показывается и не применяется;
- **большинство фреймов никуда не попадает** — на строку вне функций, в
  другую функцию (если фреймы не восстанавливались по маппингу) или в файл,
  которого здесь нет — одна строка называет сборку
  из отчёта: рабочее дерево не соответствует ей, и номера строк не имеют
  смысла без переключения на ту сборку.

Для минифицированной сборки фреймы сначала восстанавливаются через
`project.mapping` из конфига
([Минифицированная сборка](anr.md#минифицированная-сборка)); без него они не
найдутся.

Подробнее об этом сценарии — в [ANR](anr.md).

## `--pools`: именование потоков вместо разметки работы

Два предыдущих пути начинаются с кода — манифеста или стека зависания. Этот
начинается с отчёта:

```
uninstrumented_cpu   pool-7-thread-1   3184 ms   98% of CPU outside slices
```

В репозитории нет строки `pool-7-thread-1`. Это имя дал JDK из стандартной
фабрики, которую используют `Executors.new*` и голый `Thread(` (или
котлиновский `Thread { … }`). `ForkJoinPool` и
`Executors.newWorkStealingPool()` дают имена вида `ForkJoinPool-N-worker-M`,
и строка вывода говорит об этом. `grep` ничего не находит, и на этом охота
буксует.

Размечать конкретную работу здесь рано — вы ещё не знаете, что именно там
крутится. Назвать пул дешевле и не требует знаний о задачах: одна правка в
месте создания пула покрывает всё, что на нём запускается, а **каждый детектор
и так группирует по имени потока**, так что за один прогон `pool-7-thread-1`
во всём отчёте превращается в `cart-queue`. Только после этого стоит ставить
маркеры, и тогда уже понятно куда.

```bash
echolot mark --pools --root .
```

```
· app/src/main/java/…/di/RepositoryModule.kt:355   (name it)  [jdk]  Executors.newSingleThreadExecutor
· app/src/main/java/…/di/SchedulerModule.kt:24     (name it)  [jdk]  ThreadPoolExecutor
```

Автоматически здесь ничего не применяется — заглушка `(name it)` прямо
говорит об этом. Инструмент находит место вызова, но не может придумать имя:
на двух реальных проектах имена из окружающего кода получались вроде
`provideproductr`, `onauthenticatio` и `capacity`, потому что внешний символ —
это Dagger-провайдер или переменная, а назначение пула скрыто в вызове, куда
он передаётся.

**Максимум 15 символов.** Linux обрезает поле `comm` потока до 15 символов, и
в трейс попадает обрубок — `pool-12-thread-1` приходит как `pool-12-thread-`,
а главный поток `com.example.myapp` как `m.example.myapp`. Используйте
`cart-queue`, а не `CartQueueProcessorExecutor`.

Поток с уже заданным именем и пул с именованной фабрикой не попадают в
вывод. Что считается заданным именем:

- строка среди аргументов `Thread(` — `Thread(r, "io")`,
  `new Thread(r, "io-" + n)`, `Thread("sync")`, `object : Thread("sync")`;
- любой второй аргумент в конструкторе `Thread(r, name)` (кроме
  `(ThreadGroup, Runnable)`);
- фабрика с `ThreadFactoryBuilder().setNameFormat(…)` или собственным
  `newThread(`;
- фабрика, создающая потоки через `Thread(` — например,
  `Executors.newFixedThreadPool(2) { r -> Thread(r, "io") }` в Kotlin. Здесь
  решает именно этот `Thread(`: если имя есть — строки не будет; если нет —
  указывается он;
- `ThreadFactory`, переданная в `Executors.new*` (второй аргумент у
  `newFixedThreadPool` и `newScheduledThreadPool`, любой аргумент у остальных);
- `HandlerThread`, принимающий имя первым аргументом.

Учёт этих правил сократил список на одной кодовой базе с пятнадцати мест до
четырёх реальных.

## Как это встраивается в цикл

```
analyze          → отчёт называет системные срезы и потоки; domains пуст
mark --apply     → до 3 маркеров в точках входа (Application.onCreate,
                   launcher onCreate, setContent), одна команда, ~1 КБ
build, install   → режимы launch и command записывают сборку на телефоне;
                   последняя строка --apply подскажет задачу Gradle
collect, analyze → теперь отчёт пишет AGENTTMP_set_content 1200 ms self,
                   а domains указывает на MainActivity.kt:69
read one place   → агент открывает один файл из отчёта — и при необходимости
                   ставит второй, точечный слой маркеров вручную
mark --remove    → очистка, затем grep -rn -e AGENTTMP_ -e 'echolot:mark' для контроля
```

Команда находит вход и первый переход; трейс показывает, где вес; агент
открывает ровно один нужный файл. Именно такой порядок заложен в
`perf-hunter.md`.

## Две вещи, которым маркеры не нужны вообще

- **`androidx.compose.runtime:runtime-tracing`** в модуле приложения добавляет
  в трейс имена composable-функций без единой правки кода. `mark` подскажет,
  если в Compose-приложении (где есть `setContent {` или `@Composable`) этой
  зависимости нет — для такого приложения это первый шаг. Приложению без
  Compose об этом не сообщается.
- **Сэмплинг стеков вызовов** (`runner.sampling`, `linux.perf` в Perfetto)
  определяет Java/Kotlin-методы на горячем потоке по символам — без
  инструментирования и именования. Сборка должна быть `profileable`, а
  минифицированной нужен `project.mapping`. `uninstrumented_cpu` читает
  сэмплы: строка сразу называет, что крутилось в слепой зоне и какой метод
  проекта это вызвал. Подробнее — в
  [Сбор трейсов](collecting.md#сэмплинг-стеков-вызовов).

## Где инструмент ошибётся

Регулярные выражения по Kotlin и Java видят синтаксис, но не семантику.
`BaseActivity` из внешней библиотеки, владеющий настоящим `onCreate`, всё, что
создаётся через DI-граф без прямых вызовов, кодогенерация, оболочки Flutter
или React Native — `mark` найдёт точку входа, честно сообщит, за чем не может
проследить, и остановится. Это осознанный отказ: три точных маркера и
честная заметка лучше семи догадок. Дальше по шагам ведёт сам трейс.

`--pools` читает только место вызова конструктора и ничего дальше. Имя,
заданное уже после создания потока (`Thread(r).apply { name = "io" }`,
`t.setName("io")`), не распознаётся, и такой поток всё равно попадёт в
список; а `Thread(group, runnable)` имеет два аргумента и ошибочно считается
именованным. Фабрика, переданная в `ThreadPoolExecutor(…)`, не проверяется, и
такой пул попадёт в отчёт как `pool-N-thread-M`.
